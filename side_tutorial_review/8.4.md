## 8.4 — Stations 2–3 in detail: the generated stub (usys.pl), and the four things ecall does

The stub isn't something you write
— it's generated by a Perl script (usys.pl)
from a list of syscall names, producing one tiny assembly function per syscall (e.g. sysinfo:).

Each generated stub does the same pattern: load the syscall's number into a fixed register (a7 on RISC-V), then execute ecall. That's it — no logic, just "here's which syscall this is" + "trap now." This is why adding a new syscall means adding its name to the list usys.pl reads (one of the five registration sites in 8.6) — without that, there's no stub, and your C code has nothing to call into.

====================
ecall itself, once executed, does exactly four things, unconditionally, every time, and nothing else:

---

1. Saves the current PC (into sepc) so execution can resume where it left off later.

2. Records the cause (into scause) — marks this trap as an environment call from user mode, distinguishing it from an interrupt or exception (2.1's "one mechanism, three causes").

3. Flips the privilege mode to kernel (supervisor) mode.
   Jumps to a fixed address stored in a control register (stvec) — not anywhere the user program chose, always the same kernel-installed entry point.

4. Nothing else happens — no register saving beyond sepc, no stack switch, no argument passing beyond what's already sitting in registers. Everything else (saving the rest of user state, switching page tables) is software's job, done next in the trampoline (8.5).

==================

8.5 — Stations 4–6 in detail: the trampoline, usertrap's dispatch, syscall()'s table lookup

The trampoline is the landing pad stvec points to. It's one physical page, mapped at the identical virtual address in every process's page table and in the kernel's page table (4.5)

— that sameness is essential, because right after ecall fires, the CPU is still fetching instructions using the user page table for one more instruction,
and the trampoline code's job includes switching to the kernel's page table (satp from 5.7).

If the very next instruction after that switch weren't mapped at the same address in both tables,
execution would fault immediately on a page table it just switched into.

So:

trampoline code saves the rest of user register state into the trapframe (4.4 — a fixed, per-process kernel-only page holding registers/state that survive the trap), swaps satp to the kernel page table, and only then jumps into usertrap().

---

1. usertrap()
   is the single C function that handles every trap arriving from user mode — syscalls, interrupts, and exceptions alike (2.1). It reads scause to figure out which of the three this was. For a syscall specifically, it increments the saved PC by 4 (past the ecall instruction, so returning doesn't re-execute it) and calls syscall().

2. syscall()
   reads the syscall number that the stub (8.4) placed in a7 — now sitting in the trapframe's copy of that register — and uses it as an index into a table of function pointers (syscalls[]), calling whichever one matches. This is the literal implementation of "call-by-number instead of call-by-name" from 2.4: the kernel never sees the string "sysinfo", only the integer that table entry corresponds to.

===================================

8.6 — The five registration sites: six edits, five files, five failure modes

---

Adding a new syscall means touching multiple files that all have to agree on the same syscall number and name, because nothing here is dynamically discovered
— it's all hardcoded, consistent-by-hand tables. Miss one, and you get a specific, diagnosable kind of breakage:

1. user/usys.pl
   — add the syscall name to the list this script generates stubs from. Miss this → your C code calling sysinfo() fails to link (no stub function exists with that symbol name).

2. user/user.h
   — add the function prototype so C code compiles against it. Miss this → compile error (implicit declaration / type mismatch) in whatever user program calls sysinfo().

3. kernel/syscall.h
   — add a #define SYS_sysinfo <number> constant. This number is the contract between the stub (which loads it into a7) and the kernel's dispatch table (which indexes by it). Miss this / mismatch it → wrong syscall runs (whatever number happens to be there gets called instead
   — a silent, wrong-behavior failure, not a crash).

4. kernel/syscall.c
   — add the function pointer to the syscalls[] array at the matching index, and forward-declare sys_sysinfo. Miss this → runtime failure: syscall() looks up an empty/null table slot, xv6 typically prints something like "unknown sys call" and returns -1 (this is the "sys23" symptom in 8.11).

5. kernel/sysproc.c (or wherever you put it)

   — actually write sys_sysinfo(), the real handler. Miss this → link error again (table references a function that doesn't exist).

---

Five files, but the plan calls it "six edits" because syscall.c needs two separate edits (the forward declaration and the table entry) — both required, both easy to do one without the other.

===================================

8.7 — Station 7: fetching arguments you were never "passed"

Your sys_sysinfo() handler is a normal-looking C function, but it has no parameters in the usual sense — because the trap mechanism didn't call it like a function call; syscall() just invoked it via a function pointer with no arguments (2.4: registers-only argument passing isn't enough, so xv6 doesn't even try that route for syscall handlers directly). Instead, whatever the user program put in registers before ecall is sitting in the trapframe (the same structure the trampoline saved user state into, 4.4/8.5) — and your handler has to explicitly go pull values out of it.

---

xv6 provides helper functions for exactly this, layered by type:

1. argraw(n)

— the base primitive: fetch the raw register value for argument slot n directly from the trapframe. Everything else builds on this.

2. argint(n, &out)

— fetch argument n and interpret it as an integer.
argaddr(n, &out) — fetch argument n as a user-space virtual address (e.g. the pointer &info your user program passed) — still just a number until you actually use copyout/copyin to safely read/write through it.

3. argstr(n, buf, max)

— fetch argument n as a user address, then safely copy a null-terminated string from user memory into a kernel buffer, checking bounds along the way.

---

The safety angle matters: a user-space address is only meaningful in the user page table, but your handler is running with the kernel page table active (from 8.5's satp switch) — so you can't just dereference a user pointer directly. These helpers (and copyout/copyin underneath) explicitly walk the process's page table to translate and safely move data across the kernel/user boundary — this is the same safety concern that makes copyout essential in 8.9.

=======================

8.8 — Station 8: the way home — sret and the trapframe

Once sys_sysinfo() returns a value, it's stored into the trapframe's copy of the return-value register (a0) by syscall().

Control unwinds back up through usertrap(), and eventually the kernel executes the return path: restore all the other saved user registers from the trapframe, switch satp back to the user page table (again via the trampoline, for the same "must execute the switch instruction from an address valid in both tables" reason as the trip in), and execute sret — the RISC-V instruction that's ecall's mirror image: it flips the mode bit back to user mode and jumps to the PC value saved in sepc (which, recall from 8.5, was already advanced past the original ecall instruction).

---

From the user program's perspective, none of this happened — it just made a function call (sysinfo(&info)) that took some time and came back with a value in a0, exactly like any normal C function returning a value. That illusion — call, trap, kernel work, return — being indistinguishable from an ordinary function call is the entire point of the design:

the trapframe held everything needed to make the interruption invisible.

===================================

8.9 — Part B philosophy: walk a list on demand, don't keep a counter

For Part B (real data, from 8.1), the naive approach might be "maintain a running counter of free memory / process count, updated every time something allocates or a process is created/destroyed, so sysinfo can just read the counter instantly." xv6 deliberately does not do this. Instead, sysinfo's handler walks the actual data structures fresh, every time it's called:

==================

1. Free-memory walk:
   xv6 tracks free physical pages as a linked list (the free list) — each free page's first bytes literally point to the next free page. To report "how much free memory," the handler walks this list start to end, counting nodes, and multiplies by page size. No separate counter exists to go stale or get out of sync.

2. Process-table walk:
   to count "how many processes are in use," the handler iterates the fixed 64-slot proc[] array (3.5) checking each slot's state field, rather than trusting a cached count that every fork/exit would otherwise need to remember to update.
   Why walk instead of cache: a cached counter requires every place that changes the underlying state to also remember to update the counter — a maintenance burden and a bug magnet (miss one increment/decrement site, and the counter silently drifts from reality forever).
   Walking the real structure on demand is slower per call, but it's always correct by construction — there's no second source of truth to fall out of sync. Since sysinfo isn't called in a hot loop, the walk's cost is a fine trade for that guarantee.

3. copyout's safety role:
   once the handler has computed real values (free memory, process count) in kernel-local variables, it can't just write them into the user-provided struct pointer directly — same cross-page-table problem as 8.7. copyout(pagetable, user_dst_addr, kernel_src_addr, size) walks the user process's page table to translate the destination address and safely copies bytes from kernel memory into user memory, checking that the destination is actually valid, user-accessible memory along the way (preventing a buggy or malicious user pointer from making the kernel write into arbitrary/kernel memory).

==============================

8.10 — Part C: the producer/consumer shape

Part C asks for a value that reflects behavior over time (e.g. average number of runnable processes), not a single instant — which means something has to be sampling continuously in the background, independent of whenever a user happens to call sysinfo.

==================

1. The producer: xv6's timer interrupt handler, clockintr, already fires on a fixed schedule (this is the same timer-interrupt mechanism from 2.5/1.5 that also drives RR's quantum expiry). You extend it so that, on top of whatever it already does, it also takes a sample each tick — e.g. counts how many processes are currently RUNNABLE — and records that sample.

2. The ring buffer: samples get stored into a fixed-size circular buffer (a ring buffer) rather than an ever-growing list — a fixed array with a wraparound index, so old samples get overwritten by new ones once the buffer fills, keeping memory bounded regardless of how long the kernel runs.

3. The consumer: whenever sysinfo (or a related call) is invoked, it reads the accumulated samples out of the ring buffer and computes something like a running average, rather than sampling itself right there — because a single point-in-time reading wouldn't capture a trend.

=====================
That's the producer/consumer shape: clockintr produces data asynchronously in the background at its own pace; sysinfo's handler consumes/summarizes it whenever called, at a completely independent pace. Same overall shape as any producer/consumer problem — one side generates data on its own schedule, the other reads it when convenient, and the buffer between them decouples the two rates.

---

Why fixed-point integers, not floats: xv6's kernel deliberately avoids floating-point arithmetic — enabling FP registers/instructions inside the kernel requires extra context-switch save/restore work (FP register state) that xv6 doesn't bother with, and kernel code paths generally avoid FP for portability and simplicity reasons across many OS kernels, not just xv6. So an "average" here is computed using fixed-point arithmetic: representing a fractional value as an integer scaled by some fixed factor (e.g. multiply by 1000 before dividing, then remember the result is "times 1000" when interpreting it) — getting a meaningfully precise average using only integer add/multiply/divide, no float/double types anywhere in kernel code.

=================================

8.11 — Debugging checkpoints: reading symptoms back to broken stations

Since each registration site failure (8.6) produces a distinct symptom, you can localize a bug just from what you see:

---

1. "Nothing shows up at all" / total silence, or the syscall doesn't even compile → almost certainly stations 1–2: missing usys.pl entry (link failure) or missing prototype in user.h (compile failure). Check those two files first.

2. "Unknown sys call" / prints the raw number like "sys23" (i.e., the kernel got a syscall number it doesn't recognize, and just echoes the number back since it has no name for it) → SYS_sysinfo is defined in syscall.h but the corresponding entry is missing or misindexed in the syscalls[] table in syscall.c (station 6) — the number arrived, but there's nothing at that table slot.

3. The syscall runs but produces wrong/garbage numbers, or crashes → the plumbing (stations 1–6) is fine, and the bug is inside your handler logic itself — likely a bad argaddr/copyout (8.7/8.9), an off-by-one in the free-list or process-table walk, or (for Part C) a ring-buffer indexing bug.

Calling it "by name" works differently than expected, e.g. if you test by hardcoding a syscall number instead of going through the proper generated stub → suggests a mismatch between the number your test uses and what's actually registered in syscall.h/syscall.c — a sign the registration sites (8.6) are inconsistent with each other, not that your handler logic is wrong.

---

The general debugging principle: symptom location tells you which station to inspect — don't start reading sys_sysinfo()'s internals if the problem is actually "the stub never got generated." Work outside-in: confirm it compiles/links, confirm the table entry gets hit (even with a placeholder handler that just returns a fixed value — this is Part A's whole purpose from 8.1), then debug the handler's actual logic once the pipe itself is proven to work.
