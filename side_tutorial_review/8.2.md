//8.2 — Why a syscall can't just be a jump:
privilege mode + separate page tables, and the one door (ecall)

If a syscall were just an ordinary function call, a user program could jump straight to kernel code's address — but two hardware-enforced barriers make that impossible:

==================

1. privilaged (kernel ) mode :

From dual-mode operation (1.2): the CPU has a mode bit distinguishing user mode from kernel mode. Certain instructions and memory regions are only accessible in kernel mode.

A user-mode jump instruction has no way to also flip the mode bit

— mode transitions are only allowed through specific,
hardware-defined mechanisms (the trap mechanism from Part 2), not by any regular instruction the user program controls.

if jumping into kernel code were enough, user programs could execute arbitrary privileged instructions by just jumping into the middle of kernel code

---

2. Separate page tables.

From 5.7/4.x: each process has its own page table, and (in most designs, xv6 included with some nuance around the trampoline) the kernel's code/data isn't even mapped into a user process's page table at all, or is mapped without user-accessible permissions.

So even setting privilege mode aside, a user-mode "jump" to a kernel address might not resolve to anything valid — there's no guarantee the kernel's code lives at a usable virtual address from the user process's perspective.

=============

The one door: ecall. RISC-V provides exactly one instruction for this transition:

ecall (environment call) — a deliberate, hardware-defined trap instruction

---

Executing ecall doesn't jump anywhere the user program specifies
— instead it triggers the same generic trap mechanism from 2.2:

save state,
record why (this was a deliberate ecall,
distinguishable from an interrupt or exception via scause),
flip the mode bit to kernel mode,
and jump to one fixed, kernel-controlled entry point
(not a user-chosen address).

The kernel — not the user program — decides what happens next, by inspecting why it was called (via the register-passed syscall number, coming in 8.4) and dispatching accordingly.
