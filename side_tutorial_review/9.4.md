Step 14 -- the heartbeat: clockintr() in kernel/trap.c

clockintr()
{
  if(cpuid() == 0){
    acquire(&tickslock);
    ticks++;
    wakeup(&ticks);
    release(&tickslock);
  }
  w_stimecmp(r_time() + 5000000);    // next tick ~half a second away (GINI slows it for humans)
}

- only thing in the kernel that happens without anybody asking
- cpuid() == 0: every CPU takes a timer interrupt, only CPU 0 keeps the clock -> your sample goes inside that
  test too, or 4 CPUs would each record the same tick
- wakeup(&ticks) already walks the whole proc table taking every p->lock -> doing it from the timer is normal

Why taking p->lock inside an interrupt can't deadlock (not in the handout):
acquire() disables interrupts on this CPU (push_off). So the timer can never fire while THIS CPU holds a
spinlock -> clockintr never waits on a lock its own CPU already holds.

Step 15 -- the ring buffer + producer: load_sample()

int loadring[LOADN];
int loadi;                      // only ever goes UP

load_sample:
  n = count procs with state RUNNABLE or RUNNING   (under each q->lock)
  loadring[loadi % LOADN] = n;
  loadi++;

ring buffer = fixed array + ever-increasing index, % wraps it round
-> always holds the last LOADN samples, oldest quietly overwritten
-> no allocation, nothing to free, can't run out  (why kernels use it everywhere)

why RUNNING counts too: a process using a CPU right now IS load; it just isn't queued.
(Part B's nrunnable counts only RUNNABLE -- different question.)

=====================
Step 16 -- the consumer's math: load_avg(want)

have = loadi < LOADN ? loadi : LOADN     // how many samples actually exist
if(want > have) want = have;
if(want <= 0)   return 0;
sum the last `want` samples, newest first:  loadring[(loadi - i + LOADN) % LOADN], i = 1..want
return (sum * 100) / n;

why `have`: in the first 30 s after boot there aren't 30 s of samples. Averaging over empty (zero) slots would
report an idle machine when it's busy.
why "+ LOADN" before %: keeps the index non-negative while loadi < i.

why x100, not float:
the kernel does NOT save floating-point registers on a context switch (count them in swtch.S -- none).
A float in kernel code COMPILES, then silently corrupts another process's FP arithmetic.
-> fixed point: scale the integer by 100, divide at the end. 250 means 2.50. (Linux uses x2048.)

Step 17 -- call it from the heartbeat

inside cpuid() == 0, AFTER release(&tickslock):
    release(&tickslock);
    load_sample();

after, not before: no reason to hold tickslock while taking 64 p->locks. Hold one lock when one will do.

Step 18 -- kernel/defs.h, trap.c section:
#define LOADN 60                 // 60 samples x 0.5 s = 30 s of history
void   load_sample(void);
uint64 load_avg(int);

Step 19 -- kernel/sysproc.c, replace the placeholder:
info.load5  = load_avg(10);      // 10 samples = 5 s
info.load15 = load_avg(30);      // 30 samples = 15 s
info.load30 = load_avg(60);      // 60 samples = 30 s

Division of labour: the interrupt does the CHEAP part (one sample); the syscall does the arithmetic.
Right way round -- anything in an interrupt handler delays everything else on that CPU.

Step 20 -- printing a x100 value (the "missing step")

xv6's printf has no width or zero-padding. "%d.%d" with v/100 and v%100 turns 306 into "3.6" -- wrong, quietly.
Print one digit at a time:
  printf("%s: %d.%d%d\n", name, v/100, (v/10)%10, v%10);     // 306 -> 3.06

Run: sysinfotest, then spin 40 & (x3), then sysinfotest every few seconds for 30 s.

                      5s     15s    30s
idle                  0.00   0.04   0.04
12 s into spinners    3.30   2.80   1.57
26 s in               3.20   3.06   3.13

5 s reacts at once; 30 s still remembers the idle machine; by ~26 s they agree.
The SHAPE of the three tells you if load is arriving (5 > 30) or leaving (5 < 30) -- why uptime prints three.
Idle shows 0.04 not 0: now and then a sample catches the shell / sysinfotest itself RUNNING.
