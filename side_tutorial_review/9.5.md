//9.5 — Whatever breaks: debug by STAGE, then by STATION

Sources: ALab01_Sysinfo_Student.pdf ("Answering": introduce errors into each edit; "six things": at least one failed
build), T02 debug table, T01 "when something looks wrong"

The handout asks: break each edit on purpose and see WHICH STAGE catches it:
compiler -> linker -> runtime (loud) -> runtime (silent)
The later the stage, the harder the bug. Silent ones are the dangerous ones.

Reminder from 9.1: a kernel that fails to build leaves the OLD kernel running.
-> a compile/link error you didn't read looks exactly like "my edit did nothing". Always read the Load output.

=====================
Debug order when something is wrong

1. Did it BUILD? Read the Load output. Failed build = old kernel still running.
   compile error -> missing declaration/include/define (Steps 1,2,5,10,11,18)
   link error    -> a declared thing has no body (kernel: 4,9,15) or no stub (user: 6)
2. Does it REACH the kernel? System Calls histogram:
   nothing  -> Step 6 (stub) or Step 3 (table row)
   sys23    -> Step 1 #define doesn't match
   sysinfo  -> plumbing is fine, go to 3
3. Are the NUMBERS right? Check the CHANGE against GINI's faces (9.3), not the absolute value.
   wrong numbers with good plumbing = logic inside sys_sysinfo / freemem / load_sample / load_avg / printing

Outside-in: build -> path -> numbers. Never read the handler first when the stub might not exist.
