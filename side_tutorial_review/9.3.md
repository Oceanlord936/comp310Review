Step 9 -- count free memory: kernel/kalloc.c

free memory in xv6 = a linked list. Every free page holds a struct run { next } -- the list lives INSIDE the free pages.
so "how much is free" = count the nodes x PGSIZE

uint64
freemem(void)
{
  struct run *r;
  uint64 n = 0;
  acquire(&kmem.lock);
  for(r = kmem.freelist; r; r = r->next)
    n++;
  release(&kmem.lock);
  return n * PGSIZE;
}

why the lock is NOT optional:
another CPU can kalloc() while you walk. A list modified under you = following a next pointer into a page
that is no longer free (it now holds someone's data) -> garbage or a crash.

Step 10 -- kernel/defs.h:  uint64 freemem(void);
defs.h is how one kernel file reaches a function in another. Without it, sysproc.c cannot call freemem().

Step 11 -- walk the process table: kernel/sysproc.c

#include "sysinfo.h"
extern struct proc proc[NPROC];     // the fixed 64-slot table (3.5)
extern uint ticks;

one loop over proc[0..63], under each q->lock:
  state != UNUSED   -> nproc++, memused += q->sz
  state == RUNNABLE -> nrunnable++
  state == SLEEPING -> nsleeping++

then: freemem(), ticks under tickslock, load* = 0, copyout.

why ONE loop, not four: each loop would acquire every p->lock again (64 x 4 lock round-trips),
and one pass gives all four numbers from the same moment.

Step 12 -- the line worth slowing down for

copyout(p->pagetable, p->sz, addr, (char *)&info, sizeof(info));

addr is a USER virtual address. The kernel runs on its OWN page table, where that number means
something else or nothing.

*(struct sysinfo *)addr = info;   // compiles -- then corrupts whatever lives at that address in the KERNEL's map

copyout walks the PROCESS's page table, finds the physical frame behind addr, and writes there.
It is the only correct way for the kernel to hand data back to a program.

GINI's xv6: FIVE arguments, p->sz second. Online solutions show four -- different xv6 version, won't compile.
Worked example already in this kernel: filestat() in kernel/file.c returns a struct stat the same way.

Step 13 -- verify: check the CHANGE, not the number

GINI computes the same things a different way (a bitmap of every physical page, its own read of the
process table) -> a second opinion.

1. sysinfotest -> write down free bytes and runnable
2. spin 30 &   three times
3. sysinfotest again + open Process Scheduler and Virtual Memory

expect:
runnable 0 -> 3, and the Scheduler face agrees
free bytes drops, and the VM face's free-page count drops by the SAME amount

why runnable was 0 before (one core): when sysinfotest asks, IT is RUNNING (not RUNNABLE),
and the shell is SLEEPING in wait(). After three spinners: they queue up as RUNNABLE while you run.

The absolute numbers will NOT match exactly -- not a bug. The two count slightly different things at the
edges of memory. You will be asked about this: write down what you see.
