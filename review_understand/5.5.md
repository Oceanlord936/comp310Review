//5.5 — exit()/wait() and resource reclamation

exit() doesn't fully erase a process the instant it's called —

reclamation happens in two separate phases, split across exit() and wait(). This split is the setup for 5.6 (zombies), so it's worth being precise here.

================

Phase 1 — what exit() does immediately, by itself:

1. Closes all open file descriptors.

2. Frees the process's user memory — its page table and all the physical pages backing text/data/heap/stack. (This is the big, expensive stuff — freed right away, no reason to wait.)

3. Records the exit status (the value passed to exit()) somewhere it'll survive.

4. Changes the process's state to ZOMBIE (recall the six-state model from 3.3) — it is dead, but its PCB / process-table slot is not freed yet.

5. Wakes up the parent, in case the parent is already blocked in wait().

-->
So after exit() runs, the process has given back its memory and files, but it still occupies a slot in the process table

still holding the PID , and a note pinned to it (exit status), waiting for someone to claim it.

---

Phase 2 — what wait() does, called by the parent:

1 . Finds a zombie child (in xv6: literally scans the fixed 64-entry process table for one belonging to it).

2. Reads out that recorded exit status and hands it back to the caller.

3. Now frees the last bit of bookkeeping — the process-table slot itself goes back to UNUSED, kernel stack freed, PID freed for reuse.

==========

The reason it's split this way rather than exit() doing everything: the exit status has to go somewhere for the parent to retrieve, and the process itself can't hold onto that after its memory is torn down — so the kernel keeps a minimal leftover record (the zombie) alive specifically to carry that one piece of information across to whoever calls wait().

============

xv6 vs. Linux, the actual difference asked for here:

Both systems use this same exit→zombie→wait→reap two-phase model
— that part is identical, not a difference. The difference is in what a zombie costs while it waits to be reaped:

---

xv6:
the process table is a fixed array of 64 slots (your 3.5 note). A zombie occupies one of those 64 slots until reaped. If enough children exit without their parent ever calling wait(),
zombies pile up and can literally exhaust the entire table — at that point fork() fails for everyone on the system, because there's no slot left to allocate, not even an unrelated process's. That's the sharp, "stops the machine from starting anything" failure mode Part 5.6 references.

---

Linux: the process table is a dynamic linked list of task_structs (also from 3.5), so there's no fixed 64-slot ceiling — zombies still consume kernel memory and a PID while unreaped, but you'd need to leak an enormous number of them (bounded by memory or the much larger PID-space limit) before it caused the same kind of hard, immediate lockout xv6 hits with just 64.
