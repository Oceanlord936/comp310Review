//4.4: The trapframe

Whose is it. Each process has its own trapframe.

When the kernel creates a process (allocproc),
it allocates one physical page for it and stores a pointer in p->trapframe. That page is mapped in two places:

1. in the process's page table at the fixed vitrual address
   TRAPFRAME

2. in teh kernel's view through the pointer
   p -> trapframe,
   which is what usertrap , syscall()
   and the argument-fetching functions use

Both views point to the same physical page.

---

what is in it ???

1. All user registers: ra, sp, gp, a0–a7, t0–t6, s0–s11, and so on.

2. epc, the saved user program counter, copied from sepc.

3. Kernel-side values that the trampoline needs:
   the kernel page table (kernel_satp), the kernel stack pointer (kernel_sp), the address of usertrap (kernel_trap), and the hart ID.

---

Why your own process can't touch it ?

It has no U bit. It's part of your address space so the hardware can reach it during a trap, but user code that tries to read or write it gets a page fault. It also holds kernel values. If a user process could overwrite kernel_sp or kernel_trap, it could redirect where the kernel runs on the next trap. Keeping the page off-limits protects the kernel's own entry state.

---

How the trampoline finds it ???

The sscratch register holds the address TRAPFRAME while the process is in user mode.

The first instruction in uservec swaps a0 with sscratch. That gives the code a base register pointing at the trapframe and saves the user's a0 at the same time. From there it stores every other register into the page.

---

Why the save happens on every trap???

uservec runs before anything knows why the trap happened.

It could be a syscall, a timer interrupt or a fault. So it saves the full user state unconditionally, and only afterward does usertrap read scause and decide what to do.

That's correction #8. Saving a trapframe is not a process switch. A switch to a different process is a separate, conditional decision, made only if usertrap finds a timer interrupt and calls yield.
Most traps, such as a syscall that returns immediately, save the trapframe and return to the same process with nothing switched.

---

Trapframe vs context. Don't confuse it with the context struct from 3.7. The trapframe is user registers saved on user-to-kernel entry.

The context is kernel registers saved by swtch when the kernel switches between processes.

What happens, step by step:

1. A timer interrupt fires while the process runs in user mode.

2. uservec saves all the user registers into the trapframe. It has to, because it doesn't know yet whether this is a timer, a syscall or a fault.

3. usertrap reads scause, sees a timer interrupt, and handles it (clockintr and so on).

4. The scheduler decides the process's time slice isn't up, so there's no yield and no switch.

5. usertrapret runs, then userret restores the registers from the trapframe, and sret resumes the same process.

Right, by the time uservec runs the CPU is already in supervisor mode.
The hardware switches the mode, before the first instruction of uservec().
That's why the no-U-bit trapframe is writable at that point.

what the hardware does at the trap, all in one step:

1. copies teh PC into sepc

2. writes the reson to scause

3. records old mode in SPP (in this case USER)

4. truns off interrups , clear SIE

5. switches cpu to kernel mdoe

6. Sets the PC to stvec, which points at uservec in the trampoline.

---

What uservec does, in order:

1. Swaps a0 with sscratch. Now a0 holds the trapframe address, and the user's a0 is parked in sscratch.

2. Stores the other registers (ra, sp, t0, and so on) into the trapframe.

3. Saves the user's a0 from sscratch into the trapframe too.
   Loads kernel_sp into sp, and loads the hart ID and the address of usertrap from the trapframe.

4. Loads kernel_satp, writes it to satp, and executes sfence.vma. This is the page-table switch. From the next instruction on, the kernel's table is active.

5. Jumps to usertrap.

question:
wait , 4. truns off interrups , clear SIE . how does this happend before switch to kernel mode ? i tought thing in user mode cannot turn off interupt

The user code isn't turning interrupts off. The hardware does it, and the privilege rules only apply to instructions that software runs.

Two different things:

A user instruction trying to change sstatus.SIE gets refused, because that's a privileged CSR. That's the rule you remember.

The trap hardware is not executing an instruction from your program. It's a built-in sequence that the CPU performs automatically when a trap is taken. It changes sepc, scause, SPP, SIE and the mode directly, with no permission check, because the CPU itself is doing it.

On my numbering. I listed the six items as steps 1–6, but they're not a sequence. The hardware does all of them together as one indivisible action. In particular, "clear SIE" isn't happening "before" the mode switch. The CPU takes the trap, and all of those changes land at the same instant.
