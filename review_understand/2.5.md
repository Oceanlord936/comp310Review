Your flow, confirmed:

The CPU (kernel driver) tells the device or DMA controller what to do: which device, memory address, size, and read or write.
The CPU then goes back to other work, for example running another process.
The device or DMA controller does the transfer between the device and memory by itself.
When it finishes, it raises an interrupt signal. The CPU traps into the kernel, which handles it, for example by waking the process that was waiting.

---

The correction: DMA is not used for everything. It is used for bulk data devices such as disks and network cards. A keyboard sends a few bytes at a time, so it uses plain interrupt-driven I/O (one interrupt per keypress). The CPU takes the byte itself, and DMA would be overkill.

Neither theory is quite right. The mouse is interrupt-driven too.

How a mouse works:

The mouse hardware measures movement itself and sends small reports ("moved +3 right, -1 down, button up"). It sends them at a fixed rate, roughly 100 times a second for older mice and more for newer ones.

The controller (PS/2 or USB) receives each report and raises an interrupt. The CPU runs a short handler that reads the movement and moves the cursor.

If the mouse isn't moving, it sends nothing, so there are no interrupts and no CPU cost. There is no while (mouse_moved) loop on the CPU.

---

One nuance on USB: USB devices can't interrupt on their own. The USB host controller (hardware, not the CPU) polls the device on a schedule. It then interrupts the CPU when there is new data. So polling exists, but it is done by the controller and not by the CPU.

Was your dad right? Partly:

He was right that moving the mouse creates work. Every report causes an interrupt and a small handler run, and the cursor must be redrawn.
On an old XP machine that was already overloaded (out of RAM and thrashing the disk, or a program hogging the CPU), that extra work can make the lag feel slightly worse.

But it is tiny compared to what actually caused the lag, and not moving the mouse doesn't make the machine faster.

His explanation ("the CPU is busy processing the mouse") gets the direction wrong. The mouse isn't what keeps the CPU busy, and the lag was caused by something else.

Yes. The mouse interrupt load is tiny compared to the real causes of a lag.

Scale

A mouse sends maybe 100 to 1000 reports per second, and each interrupt handler runs for microseconds. That is a small fraction of a percent of one CPU, even on an old XP machine.

What usually causes lag, especially on old XP machines

Not enough RAM, so the system is swapping. Programs wait for pages to be read from the slow disk. This is the classic cause.
A process hogging the CPU (a runaway program, antivirus scan, startup programs).
Slow disk I/O, where the GUI has to wait on the disk.
The GUI program itself blocked while waiting for something.

Why it feels like the mouse matters: when the machine is already stuck, you notice every extra bit of slowness, and moving the mouse is how you notice the lag. But the mouse isn't causing it, and stopping the mouse doesn't fix it.

So your conclusion is right: when the GUI lags, look at what is holding the GUI up (CPU, memory, disk waits), not at the mouse interrupts.
