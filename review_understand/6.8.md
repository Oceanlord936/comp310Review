//6.8 — Proportional share: stating the ratio instead of picking a rule-based winner

Every algorithm so far (FCFS, SJF, SRTN, RR, priority) works the same way: you define some rule for comparing processes (arrival order, burst length, priority number), and at each decision point the scheduler picks a single winner according to that rule.

the output you care about is things like average waiting time or response time — properties that fall out indirectly from whatever rule you chose.

============================

Proportional-share scheduling flips the question

Instead of asking "which process should win this decision?"

you start by directly stating how much of the CPU each process is entitled to
— as a ratio. E.g.: "Process A gets 50% of the CPU, B gets 30%, C gets 20%."

The scheduler's job is no longer to apply a comparison rule — it's to make sure that, measured over a long enough window, actual CPU time allocated to each process converges to match its stated share (A really does get ~50% of total cycles, not just "wins more often" by some proxy).

===============

The shares are usually expressed as tickets — a process holding more tickets should get proportionally more CPU time. The open question this section sets up: how do you actually implement "give out CPU time proportional to tickets" as a real scheduling algorithm? Two answers follow:

6.9 Lottery scheduling — implement it with randomness (hold an actual lottery each decision point).

6.10 Stride scheduling — implement it deterministically (the same guarantee, no dice).
