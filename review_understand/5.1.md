//5.1 — fork(): one call, two returns

The confusing thing about fork() is that it's a single function call in your source code that ends up returning twice — once in the process that called it (the parent),
and once in a brand-new process that didn't exist a moment ago (the child).

---

What actually happens, mechanically:

1. your process call fork() . This is a syscall( trap into the kernel , like everything we covered)

2. The kernel makes a near- exact copy of the calling process
   -> a new PCB , a new fixed size process table slot , a fresh copy of the entire address apace
   (text , data , heap , stack - copy page by page , r copy on write depending on the implememtaion

-> xv6 does and eager full copy )

3. both process , parent and child are now independent , runnanle netities .
   they have sparate memory , spearete pcbs , sperate pid
   neither can see other's memort changes from their point .

4. fork() returns -> as there are two process
   both sitting at the isntrutcion right after the "fork" call
   it returns in both of them , with a diff value each times:

in child -> fork() return 0

in parent , fork () return the child's PID (a positive integer)

The child doesn't need to know its own PID from the return value — it can always call getpid() if it wants that.
The parent, on the other hand, usually needs to know which child this was — especially if it forks multiple children and later wants to wait()
