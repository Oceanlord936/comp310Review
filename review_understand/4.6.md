//4.6: xv6's honest confession

This is the wrap-up of Part 4. It's about what xv6 doesn't have, compared with the textbook picture.

===========================

1. no real ready queue

3.6) describes a ready queue: a list of processes waiting for the CPU. xv6 doesn't keep one.
The scheduler just scans the whole process table (all 64 slots) in a loop

looking for a RUNNABLE process, and runs the first one it finds. The "queue" is only the set of slots whose state happens to be RUNNABLE.

Cost: every scheduling decision is a full table scan.
Benefit: no list to maintain and no linked-list bugs. It's simple, and 64 slots is small.
This ties back to 3.5 (fixed array of 64 vs Linux's linked list).

============================ 2. No hardware-enforced region types. The picture labels regions "text", "data", "stack", "heap". The hardware knows none of those names. All it sees is PTE permission bits (V, R, W, X, U) on each page. "Text" is just a page with R + X. "Stack" is just a page with R + W + U. The labels are for humans. A person (or a GINI face) reads the bits afterward and says "this looks like code".

Consequence: nothing stops a page from being used as something other than its label, apart from the bits themselves. The guard page is a "region" only because someone left U off.
The kernel keeps a rough idea of size (p->sz, the top of the heap), but it doesn't keep a table of regions by type.

======================

3. The takeaway from the whole part. The address space you saw in 4.2 is really a set of pages and flag bits. The kernel enforces safety with three cheap mechanisms:

the U bit, which separates user and supervisor access
the X and W bits, which separate code and data
unmapped pages, which fault on any touch (the gap)
