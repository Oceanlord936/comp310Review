//6.1 — The objective, and the scheduler/dispatcher split

Before the individual algorithms, two foundational pieces.

The objective — what is CPU scheduling actually trying to optimize?

---

when there are more ready process than CPUs , something has to decide which ready process runs next:

That decision matters because it changes how "fast" the system feels from different angles: how long an individual job waits, how much work gets done per second overall, how snappy an interactive program feels. There's no single "best" answer
— different scheduling policies optimize for different, often conflicting things (this is exactly what 6.2's "five criteria that conflict" is about, coming next).

=============================

The scheduler/dispatcher split — two separate jobs that are easy to conflate:

The scheduler is the policy
— the algorithm that decides, given the set of ready processes, which one should run next.
This is the part people mean when they say "FCFS" or "Round Robin" or "Priority scheduling"
— it's a decision-making rule, not code that touches hardware.

---

The dispatcher is the mechanism
— the actual code that takes the scheduler's decision and makes it happen: performs the context switch (registers + satp/page table, from 5.7), switches to user mode, and jumps to the chosen process.
The dispatcher doesn't decide anything; it just carries out what the scheduler picked.

==================

Why this split matters conceptually:
it separates "what's the right process to pick"

One more term worth pinning down now since it recurs constantly: dispatch latency — the time the dispatcher itself takes to stop one process and start another.

This is pure overhead (no useful work happens during it), so any scheduling algorithm that causes more frequent switching (like small Round Robin quanta) pays more of this overhead, which becomes one of the actual quantitative trade-offs in 6.5.
