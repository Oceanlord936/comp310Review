//5.2 — exec(): replacing the program inside a process

fork() gives you a copy of the ucrrent program
exec() takes the already running processa and replace what is wrunning inside it with a completely diff program , without creating a new process.

what actully happens :

1. a process call:
   exec("some_program" , args)
   this is a syscall

2. The kernel loads teh new prorgam's executable file
   -> text , data , BSS , from disk

3. it throws away the calling process entire old address space
   -> the old text , data , hea , and stack area ll discarded.

replaces it with a fresh address space build from the new program : new text segment ,new initallized data bss , a fresh stack with argc , arch set up on it , a fresh empty heap

4. execution then starts at the new program's entry point , its main. as if that program had benn running in this process all along .

=================================
The key thing that makes this confusing at first: if exec() succeeds, it never returns.

There's no "back to the old code" moment — the old code doesn't exist anymore in this process's memory. exec() only returns (with an error code) if it fails — e.g., the file doesn't exist or isn't executable.

If it fails, you're still running the old program and get to handle the error.

===========================

What survives the swap, and what doesn't:

survives:
PID , parent PID , open file descriptos , process table slot
, PCB itself

---

discarded:

old text / data / BSS

old heap contents

old stack contents

the old code entirely

=================

So exec() changes what program a process is running, but not which process it is — same PID, same parent, same open files (this is exactly why file descriptors survive across exec() and is the whole trick behind shell redirection: set up file descriptor 1 to point somewhere, then exec(), and the new program inherits it without knowing anything special happened).

---

Why this design, rather than just "start a new process running the new program"?

Because the process identity (PID, parent, open files) is exactly the stuff a shell needs to keep stable while swapping in new code — that's the whole point of the fork+exec split you'll see in 5.3: fork() gets you a new process without a new program, exec() gets you a new program without a new process.

Combined, they let you get a new process running a new program while keeping full control at each step (e.g. redirecting stdin/stdout in the child before the exec() overwrites it).

// notice:
xv6's signature: int wait(uint64 addr) — the argument is a pointer to where the child's exit status should be stored, not a PID. Passing 0 there just means "I don't care about the exit status, don't bother writing it anywhere."

Plain POSIX C: pid_t wait(int \*status) — same idea, argument is a status pointer, not a PID.

If you actually want to wait for one specific child (say the shell forked several background jobs and wants to wait on a particular one), POSIX gives you waitpid(pid, &status, options) — xv6 doesn't have this; it only has plain wait().

--> so when write wait(0) in XV6 it is just wait for child to finish ???

Yes — exactly right. wait(0) in xv6 means:

"Wait for any one of my children to finish" (blocks until some child calls exit() or otherwise terminates).

The 0 is not about which child — it's a null pointer, meaning "don't bother writing the exit status anywhere, I don't care what value it exited with."
