// 5.4 — Reasoning drills: nested fork(), variable isolation, why fork() can't return 0 to both sides

==================

1. why fork() can't return 0 to both sides

This ties directly to 5.1. If both parent and child got 0, neither process could tell which one it is — the whole point of the different return values is to let each side branch on its identity.

Zero to the child works as a sentinel because PIDs start at 1 and are always positive, so 0 can never collide with a real PID

2. Variable isolation after fork()

Because fork() copies the entire address space (5.1), the child gets its own private copy of every variable — same values at the moment of the copy, but a completely separate copy in memory from then on.
Changes in one process are invisible to the other.

---

eg:

int x = 5 ;
int pid = fork();

if(pid == 0){
x = 100; # child
}

else{
x = 200 ; #parent
wait(0);
}

printf("%d\n" , x);

---

notice:
Both branches run printf, independently, on their own copy of x. There's no shared memory here — this is the isolation property from Part 3/4 in action.

=============

3. Nested fork() counting — the classic drill

Key rule: every process that reaches a fork() call executes it, including children created by earlier forks.

Simplest case:

fork();
fork();
printf("hi\n");

---

start: 1 process , first fork() -> 2 processes

both of those hit the second line of fork() independently
-> each becomes 2 -> 4 processes total

all 4 reach the printf -> you see hi 4 times .

---

General rule for n fork() calls in a straight line with no conditionals: 2ⁿ total processes, so 2ⁿ lines of output if there's one print statement after all of them.

===============================

eg:

fork();
fork();
fork();
printf("hi\n");
