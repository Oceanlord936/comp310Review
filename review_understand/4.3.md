//4.3: The guard page
what it is :
one page , sitting directly below teh stack
it is mapped in teh page table with R AND W set ,
but without U -> only kernel can write

what is actully blocks:

it is not no permissions at all

The bits are R + W + V
with U missing. In user mode the CPU only allows access to pages with U=1. So if a user instruction touches an address in the guard page, the hardware sees a privilege violation and raises a page fault. The kernel gets control through the usual trap path.

===============================

how it catches a stack overflow

1. The stack page is 4096 bytes, and sp (satck pointer) starts at its top.

2. A deep recursion or a big local array keeps pushing sp down.
   Once sp goes below the bottom of the stack page, the next access lands in the guard page.

3. Page fault. scause (scause tell why )shows a fault, usertrap sees it isn't a syscall or device interrupt, and the kernel kills the process.

without the guard, sp would run into the data region right below it , and the process would silently overwirte its won globals with atck frams
-> that is dangerous , with athe guard it fails immediatly and visible .

---

Why it's the cheapest safety device in the kernel.

It costs one page of address space and no extra code. It's just one page-table entry with a missing bit.
The hardware does the checking at full speed on every access.
It reuses the U-bit mechanism that already protects the kernel pages.

---

xv6 vs Linux (correction #7). Linux has guard pages too. The real difference is that xv6's guard sits in one fixed spot forever, because its stack never grows. Linux's stack grows, so its guard moves as the stack grows.

=============

!!!
One more subtlety. The guard doesn't catch everything. A function with a huge stack frame can make sp jump past the guard page in one step and land in the data region.

eal systems handle that with stack probing. It's an edge case, not part of the labs.
