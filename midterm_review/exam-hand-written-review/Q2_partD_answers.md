**✗ Check: the offset was counted twice.** Correct: **a. 20 bits, b. 18 bits.**

- Offset: 4 KB = 2¹² → 12 bits ✓.
- Logical: 256 pages = 2⁸ → **8** bits of page number. Logical address = page number + offset = 8 + 12 = **20 bits**.
  Your "8 + 12 = 20 bits of virtual page number" already included the offset, so 20 + 12 = 32 counted it twice.
- Physical: 64 frames = 2⁶ → **6** bits of frame number. Physical address = 6 + 12 = **18 bits** (your 30 has the same double count).

**Concept (not covered clearly before): two ways to get the page-number bits, same answer.**

- From the NUMBER of pages: page-number bits = log₂(number of pages). 256 pages = 2⁸ → 8 bits. (You need 8 bits to give each of 256 pages its own number.)
- From the ADDRESS size: page-number bits = address bits − offset bits. (This is the way we did EXP 7.2: 64-byte space → 6 address bits − 4 offset bits = 2.)

These are the same thing seen from two sides: address bits = page-number bits + offset bits. Questions give you one or the other:
- "256 pages of 4 KB" → you're given the page COUNT → log₂(256) = 8, then add the offset → address = 8 + 12 = 20.
- "32-bit address, 4 KB pages" → you're given the ADDRESS size → page number = 32 − 12 = 20.
Same for frames: "64 frames" → log₂(64) = 6 frame bits, physical address = 6 + 12 = 18.

Rule: page-number bits come from the NUMBER of pages, frame bits from the NUMBER of frames, then add the offset ONCE. (Same check: 256 pages × 4 KB = 2²⁰ bytes = 1 MB logical space → 20 bits ✓.)

**✗ Check: don't convert words to bytes.** Correct: **a. 16 bits, b. 15 bits.**

The address here counts WORDS (the machine is word-addressed), so a page of 1024 words needs 1024 = 2¹⁰ different offsets → **10 offset bits**. You never need the word size.

- Logical: 64 pages = 2⁶ → 6 bits, + 10 offset = **16 bits**
- Physical: 32 frames = 2⁵ → 5 bits, + 10 offset = **15 bits**

(Your version turned 1024 words into 0.5 KB and then mixed 5 and 10 offset bits together.)

**What is a "word"?** The CPU's natural unit of data, the size it loads/stores and computes with in one go. It depends on the machine: 2 bytes on old 16-bit CPUs, 4 bytes on 32-bit ones, 8 bytes on 64-bit ones. (On RISC-V a "word" is 4 bytes, an 8-byte value is a "doubleword".) There's no single fixed size, which is exactly why D5 is set up so you don't need it: it counts everything in words.

- Word-addressed (D5's setup): each address names one WORD. 1024 words per page → 1024 different addresses per page → 10 offset bits.
- Byte-addressed (most real machines, xv6): each address names one BYTE. Then the question must tell you the word size. E.g. 1024 words of 4 bytes = 4096 bytes per page → 12 offset bits.

Rule: count the offset in whatever unit ONE ADDRESS points to. If the question only says "words" and gives no word size, it means word-addressed: just use the word count.

So: when the page size is given in the SAME unit that one address points to, no conversion is needed; the 2^x is counted in that unit.
- "4 KB pages" on a byte-addressed machine → 4096 bytes = 2¹² → 12 offset bits.
- "1024-word pages" on a word-addressed machine → 1024 words = 2¹⁰ → 10 offset bits.

Convert only when the units DON'T match, e.g. page size given in words but the machine is byte-addressable with 4-byte words → 1024 words × 4 = 4096 bytes → 12 offset bits.

Default: if the question says nothing about addressing, assume byte-addressable (real machines, xv6). Exception: if it only talks in words and gives no word size (like D5), it means word-addressed.

D6. What is the purpose of paging the page tables?

when a process populate the memory space there will only be internal frag at the last page , and no external frag

eaiser for many process to change place map around

**✗ Check: that's the benefit of paging memory, not of paging the PAGE TABLE.**

Wording first (the question is easy to misread): "paging the page table" does NOT mean "having a page table". Every paging system has a page table, even with 1 level. It means applying paging TO THE TABLE ITSELF: chop the table into page-sized pieces, store each piece in any free frame, and keep a small top-level table (directory) that says where each piece is.

- 1 level: the page table is one big array that must sit in one contiguous block of physical memory. The table itself is NOT paged.
- 2+ levels: the table's pieces are pages scattered in frames, found through the directory. The table IS paged.

Paging the page table = multi-level page tables (L07 section 7). Purpose:

1. A single linear page table is huge: 32-bit, 4 KB pages, 4-byte PTEs → 2²⁰ × 4 B = 4 MB per process, and it would have to be one CONTIGUOUS 4 MB block of physical memory (hard to find, the same external-fragmentation problem again).
2. Paging the table splits it into page-sized pieces, so each piece fits in any free frame. No big contiguous block is needed.
3. Pieces for unused parts of the address space are never created (their directory entry is just invalid). Most of a process's address space is empty, so this saves a lot of memory.

Cost: one extra memory access per level on a TLB miss.

D9. With paging, a process cannot access memory it does not own. How does the OS enforce this? Briefly explain.

OS does not allow memory access outside that process' own memory space , anything out is a page fault

**Check: right direction, but say HOW.** "The OS doesn't allow it" needs the mechanism:

1. Each process has its OWN page table, built only by the OS.
2. A process can only produce virtual addresses, and the MMU translates EVERY access through that process's page table (satp points to it). So it can only ever reach the frames the OS put in its table.
3. Pages it doesn't own have the valid bit = 0 → the MMU traps (page fault) → the OS kills the process. Protection bits (R/W/X, U) also stop e.g. writing to code or user access to kernel pages.
4. Only the kernel can change page tables or satp (privileged), so a process can't map someone else's frames into its own table.

D10. What advantage do inverted page tables have over forward page tables?

**Concept: inverted page table** (prof skimmed it, so here's the idea)

Normal (forward) page table: ONE table PER PROCESS, one entry per VIRTUAL page, indexed by page number. Entry = frame number.

Inverted page table: ONE table for the WHOLE SYSTEM, one entry per PHYSICAL FRAME. Entry i says which (process id, virtual page) is currently stored in frame i.

```
forward (per process):   page → frame        indexed by page number
inverted (whole system): frame → (pid, page)  indexed by frame number
```

Translating (pid, page): search the inverted table for the entry that holds (pid, page). The INDEX where you find it is the frame number. Then physical address = frame × page size + offset.

**Answer D10 (advantage): much less memory for page tables.** The table size depends only on how much physical memory there is (one entry per frame), not on how big the virtual address spaces are or how many processes run.
Example: 4 GB RAM with 4 KB frames = 2²⁰ frames → one table of about 1 M entries for the whole machine. With forward tables, every process needs its own (and 100 processes with 4 MB linear tables = 400 MB, EXP 7.4).

======================================

D11. What is the disadvantage of inverted page tables?

**Answer D11 (disadvantages):**

1. **Slow lookup.** The table is indexed by frame, but the CPU gives a (pid, page). So you must SEARCH the table for that pair, potentially the whole table, on every TLB miss. Fix: a hash table on (pid, page) to find the entry quickly, plus the TLB so most accesses never search.
2. **Sharing is hard.** Each frame has exactly one entry holding ONE (pid, page). So the same frame can't easily be mapped into several processes (shared libraries), which forward tables do easily (same frame in several tables).

D12. ★ What is the difference between internal and external fragmentation? (Prof: also say when each one is a concern.)

internal means within the page ,
when placing process in there will be leftover .

external is when use continiou memory placing , the free slot become scattered , each is too small to hold any process but add togteher can be large amount wasted memory space .

**Check: right idea, make it general and add "when it's a concern".**

- **Internal fragmentation**: memory is handed out in fixed-size units (pages, blocks, fixed partitions), so a process gets MORE than it asked for; the unused part INSIDE its allocation is wasted. Not only pages: any fixed unit. E.g. 10 bytes in a 1024-byte page wastes 1014.
- **External fragmentation**: with variable-size contiguous allocation, the free memory gets split into many scattered holes. In total there's enough free memory, but no single hole is big enough for the request. ✓ (your description)

When each one is a concern:
- Internal: when the allocation unit is large compared to the requests (big pages, many small processes/allocations). Smaller units reduce it but cost bigger page tables.
- External: when memory is allocated contiguously with variable sizes and processes come and go for a long time (first fit loses about ⅓ of memory by the 50-percent rule). Fixes: compaction (needs execution-time binding, costly) or paging (no external fragmentation).
