Notie:
The example is a toy machine with tiny numbers so you can work by hand. The method is exactly the same for 32-bit addresses; only the numbers get bigger.

The setup (this is EXP 7.2 from the slides):

A process's logical address space is 64 bytes, addresses 0–63.

The page size is 16 bytes, so the process has 64 / 16 = 4 pages, numbered 0–3

Physical memory (RAM) is also cut into 16-byte frames: frame 0 is bytes 0–15, frame 1 is bytes 16–31, and so on.

What "0→3, 1→7, 2→5, 3→2" means:
the page table is just an array indexed by page number, and each entry holds a frame number:

page table[0] = 3 → this process's page 0 is stored in physical frame 3

page table[1] = 7 → page 1 is in frame 7
page table[2] = 5 → page 2 is in frame 5
page table[3] = 2 → page 3 is in frame 2

The process thinks its memory is one tidy block from 0 to 63. In reality the four pieces are scattered around RAM, and the page table records where each piece went:

LOGICAL (what the process sees) PHYSICAL RAM (16-byte frames)
page 0: bytes 0–15 ───────────┐ frame 2: bytes 32–47 ← page 3
page 1: bytes 16–31 ─────┐ └───→ frame 3: bytes 48–63 ← page 0
page 2: bytes 32–47 ──┐ │ frame 5: bytes 80–95 ← page 2
page 3: bytes 48–63 │ └─────────→ frame 7: bytes 112–127 ← page 1
└── etc.

What 117 means: it's simply byte number 117 in RAM, counting from byte 0. Logical address 21 is in page 1 (bytes 16–31), at position 5 inside it. Page 1 lives in frame 7, which covers bytes 112–127. Position 5 inside frame 7 is 112 + 5 = 117.

The same thing in bits, which is how real hardware does it: 64 bytes needs 6-bit addresses, and a 16-byte page needs a 4-bit offset

====================
does the page size (vertual) and the hardware frame size need to match ??

Yes. The page size and the frame size are always the same. That's part of how paging is defined.

Why they must match:

A page has to fit exactly into one frame. If pages were bigger than frames, a page wouldn't fit. If they were smaller, part of every frame would be wasted.

The offset passes through unchanged. Offset 5 in the page becomes offset 5 in the frame. That only works if both are the same size, so they have the same number of offset bits. In the toy example, 16-byte pages and frames both use a 4-bit offset.

What can differ is the number of pages and frames:

A process can have more pages than RAM has frames; the extra pages sit on disk, which is L08.

RAM is usually bigger than one process, so there can be more frames than one process's pages

On whether the OS can pick the page size: no, not freely.

1. The hardware fixes the page size.
   The MMU is a circuit built to split addresses at one particular bit position. An OS can't just decide on 64-byte pages if the MMU doesn't support them.

2. The size is always a power of 2. That way the offset is exactly the low bits of the address, and splitting an address costs nothing: you just cut the wires. A 1000-byte page would need a real division on every memory access.

3. Real CPUs offer a few sizes, and the OS picks from those.

architecture normal page "huge" pages
x86-64 : 4 KB 2 MB, 1 GB
RISC-V : Sv39 (xv6) 4 KB 2 MB, 1 GB

xv6 only uses 4 KB.
Linux can use huge pages for large programs like databases.

4. The PTE size is also set by the hardware, as you said.

It's 4 bytes on 32-bit designs and 8 bytes in Sv39, because it has to hold a frame number plus the flag bits.

3. Page table entry (PTE) bits

Each page has one PTE,
which holds a "frame number" plus these "bits":

(1) valid: is this page part of the process at all? If not, accessing it traps.

(2) protection: R/W/X, and U, meaning user mode may access it.

(3) present: is the page in RAM right now, or out on disk? This matters for L08.

(4) dirty : has the page been written to?

(5) accessed / reference:

has the page been used recently? Page replacement in L08 uses this.

it has hit / miss rate

Hit: the translation is inside the TLB , so there is not page table walk and you go straight into memory physicall location

Miss:

It works beacuse of "locaity"

- "Spatial" :
  a 4KB page hols many nearby bytes , so only the "first" acces to each page misses .

eg: loopong over an array misses once per page , and it jits for the rest of the page

  recently used pages get used again , so running the same loop

It's physical hardware:

a small, very fast memory built inside the CPU, as part of the MMU. It isn't in RAM at all, and the kernel doesn't allocate any space for it.

The three structures we've seen, side by side:

(1) TLB . it is a hardware inside cpu / MMU
the hardware fills it automatically on a miss
the OS can only "flash" it with "sfence.vma"

(2) page table , it live in side kernel memory space

(3) PCB (Process Control Block)
it is the "struct proc" live inside kernel memory space

it is only managed by OS

---

What this means in practice:

It's tiny, with roughly tens to a few thousand entries. That's why locality matters so much.
It's fast because it's on the chip. Checking it costs about nothing, which is why the EAT formula treats the TLB lookup as free.

On RISC-V and x86, the OS can't read or write TLB entries one by one. On a miss, the hardware walks the page table and fills the entry itself. The OS's only control is "flush." Some older designs, like MIPS, had a software-managed TLB where a miss trapped to the OS, but you don't need that for this course.

It's like the other CPU registers (PC, satp, relocation/limit): one set per core, built into the CPU, and never part of memory.

9. Other table designs, plus protection and sharing

(1) Hashed page table: hash the VPN to pick a bucket, then follow a chain to find the entry.

(2) Inverted page table: one entry per physical frame instead of one per page, storing (pid, page). The table is small, but finding an entry means searching it, which is slow.

(3) Protection is per page, through the valid bit and the R/W/X/U bits.

(4) Sharing: map one frame into several processes' page tables. This works for read-only shared code, such as libc. xv6 only shares the trampoline page this way.

Terminology: "address space" = the RANGE of addresses a process can use (0 … size−1), not how much it actually uses.
64-byte address space → addresses 0–63 → 6-bit logical address. (Here the process fills all 4 pages, so the two look the same;
on real machines they differ, e.g. Sv39 address space = 2³⁹ bytes, a process uses a few MB.)
Exam phrasings that mean the same: "64-byte logical address space" = "6-bit logical addresses"; "32-bit machine" = 32-bit logical address.
Physical memory size is given separately → physical address bits.

fix: do logical and physical SEPARATELY, offset is shared.

|          | size       | address bits | − offset bits | = number bits                        |
| -------- | ---------- | ------------ | ------------- | ------------------------------------ |
| logical  | 64 B = 2⁶  | 6            | 4             | **VPN = 2 bits** (4 pages)           |
| physical | 128 B = 2⁷ | 7            | 4             | **frame number = 3 bits** (8 frames) |

offset = **4 bits** (16 = 2⁴), same on both sides.
(VPN + offset = logical address length. Frame + offset = physical address length.)

one hex digit = 4 bits, so with a 4-bit offset: last hex digit = offset, the rest = page number.

| logical | page | offset | page 4 → frame 0x66 | physical  |
