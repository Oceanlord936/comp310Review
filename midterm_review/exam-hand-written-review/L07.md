# Round 7: L07 Paging and Address Translation

---

## 1. Why paging

Base + limit needs each process to sit in **one contiguous block**, and that causes external fragmentation (EXP 6.4).

Paging fixes this:

- Split each process's logical memory into fixed-size **pages**.
- Split physical memory into **frames** of the same size.
- Any page can go in **any** free frame, so a process's pages can be scattered anywhere.

Result: **no external fragmentation**, because any free frame fits any page.

Cost: only **internal fragmentation**. The last page of each allocation is partly empty: less than 1 page per allocation, at most **P − 1 bytes** for page size P.

---

## 2. Splitting an address

```
logical address = [ page number (VPN) | offset ]
```

- **Offset bits = log₂(page size)**, i.e. "2 to what power = page size in bytes".
  xv6: pages are 4 KB = 4 × 1024 = 2¹² bytes → offset is **12 bits**.
- Only the **page number** is looked up in the page table, which gives a **frame number** (PFN).
- The **offset passes through unchanged**, because the byte sits at the same position inside the frame as it did inside the page.

```
PA = frame × pagesize + offset      (same as (PFN << offset_bits) | offset)
```

### Toy example: 16-byte pages, page table 0→3, 1→7, 2→5, 3→2

The numbers are tiny so you can work by hand. The method is the same for 32-bit addresses.

- The process's logical address space is **64 bytes** (addresses 0–63). Pages are 16 bytes → 64 / 16 = **4 pages** (0–3).
- Physical RAM is cut into 16-byte **frames**: frame 0 = bytes 0–15, frame 1 = bytes 16–31, …

**What "0→3, 1→7, 2→5, 3→2" means**: the page table is an **array indexed by page number**; each entry holds a frame number.

```
page table[0] = 3   → this process's page 0 is stored in physical frame 3
page table[1] = 7   → page 1 is in frame 7
page table[2] = 5   → page 2 is in frame 5
page table[3] = 2   → page 3 is in frame 2
```

The process thinks its memory is one tidy block 0–63. In reality the four pieces are scattered around RAM:

```
LOGICAL (what the process sees)      PHYSICAL RAM (16-byte frames)
page 0: bytes  0–15   →  frame 3: bytes  48–63
page 1: bytes 16–31   →  frame 7: bytes 112–127
page 2: bytes 32–47   →  frame 5: bytes  80–95
page 3: bytes 48–63   →  frame 2: bytes  32–47
```

**Translate logical 21:**

- page = 21 / 16 = **1**, offset = 21 mod 16 = **5**
- page 1 → frame **7**
- PA = 7 × 16 + 5 = 112 + 5 = **117**

**What 117 means**: simply byte number 117 in RAM, counting from 0. Frame 7 covers bytes 112–127, and position 5 inside it is 117.

**Same thing in bits** (how the hardware does it). 64 bytes → 6-bit logical address; 16-byte page → 4-bit offset.

```
logical 21  =  01 | 0101        page 1, offset 5
               ↓ page table: 1 → 7
physical    = 111 | 0101  = 117  frame 7, same offset
```

The hardware just replaces the page bits with the frame bits and copies the offset.

### Q: Do page size and frame size have to match?

**Yes, always.** That's part of how paging is defined.

- A page has to fit exactly into one frame.
- The offset passes through unchanged, which only works if both have the same number of offset bits.

What *can* differ is the **number** of pages vs frames:

- A process can have more pages than RAM has frames (extras sit on disk, L08).
- RAM usually has more frames than one process has pages.

So the page-number bits and frame-number bits can be different lengths; the offset bits are the same.

### Q: Can the OS pick any page size (64 B, 4 KB, …)?

**No, not freely.**

1. **The hardware fixes the page size.** The MMU is a circuit built to split addresses at a particular bit position.
2. **Always a power of 2**, so the offset is exactly the low bits and splitting an address is free (no division).
3. **Real CPUs offer a few sizes; the OS picks from those.**

Both x86-64 and RISC-V Sv39 (xv6) use 4 KB as the normal page size, and both also support "huge" pages of 2 MB and 1 GB.

xv6 only uses 4 KB. Linux can use huge pages for big programs like databases.

4. **PTE size is also set by hardware**: 4 bytes on 32-bit designs, 8 bytes in Sv39 (frame number + flag bits).

A PTE either holds a **frame number** (last level) or points to a **lower-level page table** (upper levels of a multi-level table, section 7).

Exam toy sizes (64-byte pages) are just to keep the arithmetic small.

---

## 3. Page table entry (PTE) bits

Each page has one PTE, which holds a **frame number** plus these bits:

1. **valid**: is this page part of the process at all? If not, accessing it traps.
2. **protection**: R/W/X, and **U** (user mode may access it).
3. **present**: is the page in RAM right now, or out on disk? (L08)
4. **dirty**: has the page been written to?
5. **accessed / reference**: has the page been used recently? (page replacement, L08)

---

## 4. The two problems with paging

1. **Too slow**: every load/store now needs an **extra memory access** to read the PTE first, so memory access takes twice as long. Fix: **TLB** (section 5).
2. **Too big**: 32-bit address space with 4 KB pages → 2³² / 2¹² = **2²⁰ pages**. With 4-byte PTEs the table is 2²⁰ × 4 B = **4 MB for every process**. Fix: **multi-level page tables** (section 7).

---

## 5. The TLB fixes "too slow"

The **TLB** (translation lookaside buffer) is a small, very fast **hardware** cache inside the MMU. It stores recent translations **VPN → PFN**.

- **Hit**: translation is in the TLB → no page-table walk, go straight to the physical location.
- **Miss**: the hardware walks the page table in memory, uses the result, and **stores it in the TLB** for next time.

It works because of **locality**:

- **Spatial**: a page holds many nearby bytes, so only the **first** access to each page misses. Looping over an array misses once per page and hits for the rest of that page.
- **Temporal**: recently used pages get used again, so running the same loop a second time gives all hits.

### Effective access time (EAT)

t_m = one memory access (a fixed time like 10 ns), k = number of page-table levels, h = hit rate, TLB lookup taken as free.

```
EAT = h · t_m  +  (1 − h) · (k·t_m + t_m)
      hit: 1 access   miss: k accesses to walk the k levels + 1 for the data
```

**Example**: t_m = 10 ns, k = 3, h = 0.9

EAT = 0.9 × 10 + 0.1 × (3 × 10 + 10) = 9 + 4 = **13 ns** (vs 40 ns every time without a TLB).

### Q: Is the TLB hardware, or something the kernel allocates in memory?

**Hardware**: a small, fast memory built **inside the CPU** (part of the MMU). Not in RAM; the kernel allocates nothing for it.

Compare the three things we've seen:

- The **TLB** is hardware inside the CPU/MMU. The hardware fills it by itself on a miss; the OS can only **flush** it (`sfence.vma`).
- The **page table** lives in RAM (kernel memory). The OS builds it, and the hardware **reads** it during a walk.
- The **PCB** (`struct proc`) also lives in RAM (kernel memory), and only the OS uses it.

- **Tiny** (tens to a few thousand entries), which is why locality matters.
- **Fast** because it's on chip, which is why EAT treats the lookup as free.
- On RISC-V and x86 the OS can't read/write TLB entries one by one; its only control is "flush".
- Like other CPU registers (PC, satp, relocation/limit): one set per core, never part of memory.

---

## 6. The TLB and context switches

TLB entries belong to **one** address space: VPN 5 in process A and VPN 5 in process B are different pages. So on a switch, the OS must either:

1. **flush** the TLB (empty it), so the new process starts with all misses, or
2. **tag** each entry with an **ASID** (address-space ID), so entries from different processes can live side by side.

**xv6**: no ASIDs, and the kernel has its **own separate page table**. So **every trap** switches **satp** (the register pointing to the current page table) and runs `sfence.vma` (flushes the TLB), once on the way into the kernel and once on the way out.

→ **One system call = 2 page-table switches = 2 TLB flushes.** Linux avoids this by mapping the kernel into every process's page table.

### Q: So xv6 throws something away on every syscall / timer interrupt?

**Only the TLB, not the page table.** The page tables stay in memory, untouched. After a flush, the next accesses miss, the hardware walks the table again, and the TLB refills.

**It happens on every trap, even without a process switch:**

```
user code (A's page table)
   │  trap: syscall, timer interrupt, fault…
   ▼  uservec: satp = kernel page table, sfence.vma   ← flush #1
kernel code
   ▼  userret: satp = A's page table, sfence.vma      ← flush #2
user code (A again)
```

With a process switch (timer → scheduler picks B), it's still two flushes: the return just loads **B's** page table instead of A's.

---

## 7. Multi-level (hierarchical) page tables fix "too big"

Idea: **page the page table itself**. The top level is a small **page directory** whose entries point to lower-level page tables.

**32-bit address, 4 KB pages, 4-byte PTEs:**

- offset = 12 bits (4 KB = 2¹²)
- one 4 KB page holds 4096 / 4 = **1024 PTEs** → need 2¹⁰ = 1024 → **10 index bits**
- split: **10 | 10 | 12**

```
[ 10: directory index | 10: table index | 12: offset ]
```

**General rule: index bits per level = log₂(page size / PTE size).**

- **Why it saves memory**: if a whole region is unused, its directory entry is marked invalid and **no lower-level table exists** for it. Most of a process's address space is empty, so most of those tables are never created.
- **Cost**: k levels = **k memory accesses per walk** (the k in EAT), which is why the TLB matters even more.
- **Leftover bits**: if the bits don't divide evenly, the **short field goes at the top**.
  Why: every lower-level table should be exactly one full page (fits one frame, no waste). There are many lower tables but only one top table, so the one partly-empty table should be the top one.

---

## 8. Sv39 (what xv6 uses on RISC-V)

Facts: **39-bit** virtual addresses, **4 KB** pages, **8-byte** PTEs.

- 4096 / 8 = **512 PTEs** per page → 2⁹ = 512 → **9 bits** per level
- 4 KB = 2¹² → **12-bit** offset
- 39 − 12 = 27 bits of page number, 27 / 9 = **3 levels**
- split: **9 | 9 | 9 | 12**

The **satp** register selects Sv39 mode and points to the top-level table.

---

## 9. Other table designs, protection, sharing

1. **Hashed page table**: hash the VPN to pick a bucket, then follow a chain to find the entry.
2. **Inverted page table**: **one entry per physical frame** (not per page), storing (pid, page). Small table, but finding an entry means searching it → slow.
3. **Protection is per page**: valid bit + R/W/X/U bits.
4. **Sharing**: map **one frame** into several processes' page tables. Works for read-only shared code like libc. xv6 only shares the **trampoline** page this way.

# Problems

## EXP 7.1: page size vs internal fragmentation

**1. Pages are 256 bytes. Processes A, B, C need 1030, 750, 510 bytes of memory. How many pages does each one need, and how many bytes are wasted (internal fragmentation) in total?**

Round each size up to a whole number of pages; waste = pages × 256 − size.

- A needs 1030 bytes. 4 pages is only 1024 (6 bytes short), so it needs **5 pages** = 1280 bytes. Waste = 1280 − 1030 = **250**.
- B needs 750 bytes, so **3 pages** = 768 bytes. Waste = 768 − 750 = **18**.
- C needs 510 bytes, so **2 pages** = 512 bytes. Waste = 512 − 510 = **2**.

Total internal fragmentation = 250 + 18 + 2 = **270 bytes**.

**2. Pages are 1024 bytes. Two requests: 10 bytes and 1500 bytes. How many pages and how many wasted bytes for each?**

- 10 bytes needs **1 page** (1024 bytes), so 1024 − 10 = **1014** bytes are wasted.
- 1500 bytes needs **2 pages** (2048 bytes), so 2048 − 1500 = **548** bytes are wasted.

**3. For any page size P, what is the most that one allocation can waste?**

Worst case: the request is 1 byte more than a whole number of pages, so it needs a full extra page and uses 1 byte of it → **P − 1 bytes**.

**4. What is the argument for small pages, and what is the argument against them?**

- **For small pages**: less internal fragmentation (waste is less than one small page).
- **Against small pages**: more pages per process → more PTEs → **bigger page tables**; and each TLB entry covers less memory → **more TLB misses**.
- (Big pages are the reverse: smaller tables and fewer misses, but more waste in the last page.)

## EXP 7.2: translating addresses

Setup: the process's **logical address space is 64 bytes** (logical addresses 0–63). Pages are **16 bytes**. Page table: page 0 → frame 3, page 1 → frame 7, page 2 → frame 5, page 3 → frame 2.

**1. Translate logical addresses 0, 21, 40, 63 to physical addresses.**

page = address / 16, offset = address mod 16, PA = frame × 16 + offset.

- Logical 0 is page 0, offset 0. Page 0 is in frame 3, so physical = 3 × 16 + 0 = **48**.
- Logical 21 is page 1, offset 5. Page 1 is in frame 7, so physical = 7 × 16 + 5 = **117**.
- Logical 40 is page 2, offset 8. Page 2 is in frame 5, so physical = 5 × 16 + 8 = **88**.
- Logical 63 is page 3, offset 15. Page 3 is in frame 2, so physical = 2 × 16 + 15 = **47**.

**2. Physical memory (RAM) is 128 bytes. How many bits are in (a) the offset, (b) the logical page number (VPN), (c) the physical frame number?**

Terminology: **"address space"** = the RANGE of addresses a process can use (0 … size − 1), not how much it actually uses. A 64-byte address space → addresses 0–63 → **6-bit logical address**. (Here the process fills all 4 pages, so the two look the same. On real machines they differ: Sv39's address space is 2³⁹ bytes, but a process might use a few MB.)
Exam phrasings that mean the same: "64-byte logical address space" = "6-bit logical addresses"; "32-bit machine" = 32-bit logical address. Physical memory size is given separately → physical address bits.

Rule: an N-bit address names 2ᴺ bytes. Do logical and physical **separately**; only the offset is shared.

- Offset: a page is 16 bytes = 2⁴, so the offset is **4 bits**. This is the same on both sides.
- Logical side: the address space is 64 bytes = 2⁶, so a logical address is 6 bits. VPN = 6 − 4 = **2 bits** (which gives 4 pages, matching the 4-entry page table).
- Physical side: RAM is 128 bytes = 2⁷, so a physical address is 7 bits. Frame number = 7 − 4 = **3 bits** (which gives 8 frames, and frames 3, 7, 5, 2 all fit).

Trap: "VPN = offset bits + frame bits" is wrong. Offset + frame = the **physical** address length (7). VPN + offset = the **logical** address length (6).

Seen with address 21:

```
logical  21  =  01 | 0101     (6 bits: VPN 01 | offset 0101)
physical 117 = 111 | 0101     (7 bits: frame 111 | offset 0101)
```

**Fun fact (for understanding): VPN and frame number have different widths, so how do they map?**

The page bits are NOT converted into frame bits by a formula. The VPN is used as an **index** into the page table, and the entry it finds **holds** the frame number. It's a lookup, not a calculation.

```
logical 21 = 01 | 0101
              │  use 01 (= 1) as the index
              ▼
        page table: [0] = 011, [1] = 111, [2] = 101, [3] = 010
              │  entry [1] contains 111
              ▼
physical  = 111 | 0101 = 117
```

The VPN (2 bits) only has to be wide enough to choose one of the 4 rows. Each entry has room for a 3-bit frame number, enough to name any of the 8 frames. Like an array of 4 elements holding values up to 7.

It's not one-to-one, and that's normal: this process uses only 4 of the 8 frames (3, 7, 5, 2). The other frames belong to other processes, the kernel, or are free. Each process has its own page table. The mapping only goes virtual → physical. The OS writes the entries; the hardware only reads them.

**Why are virtual and physical sizes different at all? Isn't that wasteful?**

No. They measure different things. Virtual address bits are set by the CPU design and decide how big each process's address space is. Physical address bits depend on how much RAM the machine has. Nothing ties them together.

Case 1, virtual bigger than physical (normal today): xv6 on Sv39 gives each process 2³⁹ = 512 GB of virtual space, while the machine might have 8 GB of RAM. Each process gets a roomy layout (code at the bottom, stack at the top, big gap between). Unused virtual addresses cost nothing: no frame, and with multi-level tables not even a page-table entry. Extra pages beyond RAM can go to disk (L08).

Case 2, physical bigger than virtual: old 32-bit x86 with PAE gave each process only 4 GB of virtual space but could address 64 GB of RAM. The toy example (64 B virtual, 128 B physical) is this case.

No waste either way: an unmapped virtual page is just an unused number, and an unused frame belongs to someone else or is free.

**Catch with case 2: adding RAM doesn't help one big process.**

A single process can never use more memory than its virtual address space, no matter how much RAM you add, because every byte it uses needs an address. On 32-bit x86 one process was stuck at 4 GB (really 2–3 GB, since the kernel took part of each address space). Extra RAM still helped run many processes at once and gave the OS more file cache.

Workarounds: split the work across several processes, or "remap a window" (ask the OS to change which frames part of the address space points to, like flipping pages in a book, only 4 GB visible at a time). Clumsy.

The real fix was a new CPU with 64-bit addresses. That's essentially why everyone moved to 64-bit around 2003–2005: databases and games hit the 4 GB wall. Now we're back in case 1.

Summary: physical address bits limit the whole machine; virtual address bits limit each process.

**3. A different, larger machine (same 4-bit offset): page 4 maps to frame 0x66. Translate logical 0x45 and 0x4F. Which part of the address changed?**

One hex digit = exactly 4 bits. With a 4-bit offset, the **last hex digit is the offset** and the rest is the page number.

- 0x45 splits into page 4, offset 5. Page 4 is in frame 0x66, so physical = **0x665**.
- 0x4F splits into page 4, offset F. Same frame, so physical = **0x66F**.

Only the page-number part changed (4 → 66). The offset digit (5, F) is copied unchanged.

Shortcut: you can translate hex without converting to decimal, as long as the offset is a whole number of hex digits. 4-bit offset = 1 hex digit; 12-bit offset (xv6, 4 KB pages) = **3 hex digits**, e.g. 0x12345 = page 0x12, offset 0x345.

## EXP 7.3: TLB and EAT

**1. One memory access takes 100 ns. The page table has 2 levels. The TLB lookup itself costs nothing. Compute the effective access time when the TLB hit rate is 0.98, and again when it is 0.80.**

(Use EAT = h · t_m + (1 − h) · (k·t_m + t_m).)

Hit costs 1 access = 100 ns. Miss costs 2 accesses to walk the 2 levels + 1 for the data = 3 × 100 = 300 ns.

Trap: the miss part is (k × t_m + t_m) = (2 × 100 + 100) = 300, not (2 + 100). The level count multiplies the access time.

- h = 0.98: EAT = 0.98 × 100 + 0.02 × 300 = 98 + 6 = **104 ns**
- h = 0.80: EAT = 0.80 × 100 + 0.20 × 300 = 80 + 60 = **140 ns**

Compare: without a TLB every access costs 300 ns. A 98% hit rate makes paging almost free (only 4% slower than raw memory); dropping to 80% already costs 40% extra.

**2. `int a[10];` is an array of ten 4-byte ints, and the array starts at virtual address 100 (so a[0] is at 100, a[1] at 104, …). A loop reads a[0], a[1], …, a[9] once each, in order. Pages are 32 bytes. The TLB starts empty, and it is big enough that nothing is ever evicted. Of the 10 reads, how many are TLB hits, how many are misses, and what is the hit rate?**

(List each element's address, find its page = address / 32. First access to a page = miss, later accesses to the same page = hit.)

The start address of the array matters, because page boundaries are fixed (multiples of 32).

The array starts at virtual address 100. 100 / 32 = page 3, offset 100 mod 32 = 4. A page is 32 bytes, so page 3 only has 32 − 4 = 28 bytes left for the array. Each int is 4 bytes, so 28 / 4 = **7 ints** fit in page 3 (a[0] … a[6]).

- Page 3: the first read a[0] is a **miss** (TLB empty), then a[1] … a[6] are **6 hits**.
- 10 − 7 = **3 ints** remain (a[7], a[8], a[9]) on the next page, page 4.
- Page 4: a[7] is a **miss** (new page, never touched), then a[8], a[9] are **2 hits**.

Total: **2 misses, 8 hits (6 + 2), hit rate 80%**.

Why page 4 is still a miss even though the TLB never evicts: a TLB miss only loads the translation for the **one** page you touched. "Never evicts" just means page 3's entry stays (a second run of the loop would be all hits); it doesn't mean page 4 is already there.

TLB vs CPU cache: a TLB miss loads one entry, but that one entry already covers a whole page of neighbours (32 bytes here, 4 KB on a real machine). The CPU data cache does a similar thing with a 64-byte cache line. Both use spatial locality: the TLB unit is a page and it stores a translation (page → frame), the cache unit is a line and it stores the actual data.

**3. During one system call in xv6, how many times does the kernel switch page tables, and what happens to the TLB each time?**

**2 times**, and the TLB is flushed both times.

1. Into the kernel (uservec in the trampoline): satp is set to the **kernel** page table, then `sfence.vma` flushes the TLB. The kernel code starts with an empty TLB, so its first access to each page is a miss.
2. Back to user (userret in the trampoline): satp is set back to the **process's** page table, then `sfence.vma` flushes again. The user program also restarts with an empty TLB, so its pages miss again the first time.

This is not special to system calls: it happens on **every trap**, i.e. a syscall, a timer or device interrupt, or a fault, because xv6's kernel has its own separate page table and there are no ASIDs. Even a trivial syscall like getpid() pays 2 flushes. (Linux maps the kernel into every process's page table, so a trap doesn't need to switch tables.)

## EXP 7.4: page table size and levels (your turn)

**1. A 32-bit machine (32-bit logical addresses) uses 4 KB pages and 4-byte PTEs, with a single-level (linear) page table. How big is one process's page table? How much memory do the page tables of 100 processes take?**

First find how many virtual pages there are. Offset bits come from the page size: 4 KB = 2¹², so 12 bits of offset. VPN = 32 − 12 = **20 bits**, so there are **2²⁰ pages**, which means the linear table has 2²⁰ entries (one PTE per page).

Table size = number of entries × size of one entry = 2²⁰ × 4 B = 2²² B = **4 MB per process**.

Trap: multiply by the **PTE size (4 B)**, not the page size (4 KB). 2²⁰ × 4 KB = 4 GB is the size of the whole address space the table describes, not the table itself.

100 processes, each with its own table: 100 × 4 MB = **400 MB** of page tables, even if most of those pages are never used. That's the "too big" problem, and why multi-level tables exist.

**Picture: what "size of the page table" means**

A one-level page table is just an array of rows, and each row IS one PTE. A PTE is a small record (here 4 bytes) that packs the frame number plus the flag bits:

```
one 32-bit PTE (4 bytes):
[ frame number (20 bits) | flags: V R W X U D A ... (12 bits) ]
```

The table does NOT contain the pages' data. It only says WHERE each page is. The data sits in frames elsewhere in RAM. (Like a phone book vs the houses: the book's size = lines × line size, no matter how big the houses are.)

Toy machine (EXP 7.2: 64 B logical space, 16 B pages, PTE = 1 byte), all 128 bytes of RAM:

```
PHYSICAL RAM (128 bytes)
addr
  0 ┌──────────────────────────┐
    │ frame 0  (kernel stuff)  │
    │  ┌─ PAGE TABLE ────────┐ │  ← the page table itself lives here
    │  │ row 0: 3  V R W     │ │    1 byte
    │  │ row 1: 7  V R       │ │    1 byte
    │  │ row 2: 5  V R W     │ │    1 byte
    │  │ row 3: 2  V R W     │ │    1 byte
    │  └─────────────────────┘ │    = 4 rows × 1 B = 4 BYTES total
 16 ├──────────────────────────┤
    │ frame 1  (other process) │
 32 ├──────────────────────────┤
    │ frame 2  = page 3's data │  16 bytes of real data
 48 ├──────────────────────────┤
    │ frame 3  = page 0's data │  16 bytes of real data
 64 ├──────────────────────────┤
    │ frame 4  (free)          │
 80 ├──────────────────────────┤
    │ frame 5  = page 2's data │  16 bytes of real data
 96 ├──────────────────────────┤
    │ frame 6  (other process) │
112 ├──────────────────────────┤
    │ frame 7  = page 1's data │  16 bytes of real data
128 └──────────────────────────┘
```

- The page table = the small box: 4 rows × 1 B = **4 bytes**. ← this is "size of the page table"
- The process's data = frames 2, 3, 5, 7: 4 pages × 16 B = 64 bytes. ← this is what the table points to, not the table

Same picture on the real 32-bit machine of this question:

```
PAGE TABLE (one process)             what the rows point to
┌─────────────────────────────┐
│ row 0:       frame #, flags │ 4 B ──→ a 4 KB frame of data
│ row 1:       frame #, flags │ 4 B ──→ a 4 KB frame of data
│ row 2:       invalid        │ 4 B     (no frame, but the row still exists!)
│ ...                         │
│ row 1048575: frame #, flags │ 4 B ──→ a 4 KB frame of data
└─────────────────────────────┘
  2²⁰ rows × 4 B = 4 MB              2²⁰ pages × 4 KB = 4 GB
  ↑ the TABLE (the answer)           ↑ the ADDRESS SPACE it describes
```

Row 2 is invalid but still takes 4 bytes: a linear table is indexed by page number, so it needs a row for EVERY possible page, used or not. That's why it's 4 MB even for a tiny process, and why multi-level tables skip whole chunks of unused rows.

Link to multi-level: "page size / PTE size" = how many rows fit in one page. Cut this 4 MB table into 4 KB pieces → 1024 pieces of 1024 rows each, add a 1024-row directory pointing to the pieces → that's the 10 | 10 | 12 two-level table. Pieces for unused regions are never created.

**2. A 32-bit machine uses 8 KB pages and 4-byte PTEs, with each page table taking exactly one page. (a) How many offset bits? (b) How many PTEs fit in one page-table page? (c) How many levels of page table are needed, and what is the bit split?**
