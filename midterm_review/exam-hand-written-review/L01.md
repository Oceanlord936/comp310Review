L01 — What an Operating System Is

1. What an OS is

it is a resource manager, first job is to allocate:
who gets the CPU, memory and disk, and when.

the Kernel -> the one program that runs all the time

Managing a resource means being able to "take it back"
taking the CPU back from a program that would not give it up
needs hardware: the timer interrupt

---

2. The machine underneath

Notice: CPU, memory and device controllers share one bus. Each controller is a small computer with its own buffer, and it decides for itself when it is done. The CPU cannot know a device has finished unless something tells it.

speed: an instruction takes under a nanosecond, while a disk block takes milliseconds
-> that is 6-7 ORDERS OF MAGNITUDE slower (10^6 - 10^7 times), not 6-7 times

if the CPU waited on every device it would sit idle, waiting.

so the CPU starts the device, goes back to work, and the device interrupts it when it is done.

example: at 10^9 instructions per sec, 200 disk reads x 5 ms = 1 sec of waiting per sec -> a waiting CPU is 100 percent idle.

The storage hierarchy:
registers -> cache -> main memory -> nonvolatile memory -> disk -> tape

top:    fast, small, expensive, VOLATILE (loses data on power-off)
bottom: slow, large, cheap, PERMANENT
the OS moves data between levels so programs get the speed of the top and the size of the bottom

---

3. Kernel mode and user mode

a mode bit separates user mode and kernel mode. boot starts in kernel mode, the OS then drops to user mode. a syscall traps in and flips the bit, return flips it back

Notice: think of a 2 x 2 table

user mode   + normal instruction     -> proceeds
kernel mode + normal instruction     -> proceeds
kernel mode + privileged instruction -> proceeds (already in kernel mode)
user mode   + privileged instruction -> TRAPS to the kernel !

---

the privileged ones control: I/O devices, the timer, and interrupts

no kernel code has to run to enforce this, the CPU checks the bit on every instruction by itself -> baked into a hardware check

Notice! Kernel mode is not "root"
root is a user account and runs in user mode, it just gets to ask the kernel for more. kernel mode is a CPU state, not a kind of account.

---

4. Ruling while absent:

the kernel runs about 1 in 10,000 instructions

yet stays in charge through three hardware mechanisms it sets up and then leaves:

Mode bit:    what each instruction is allowed to do

Page tables: what memory is reachable. Devices simply are not on the program's map, and the MMU checks every address at hardware level.

Timer:       the return ticket.
             it is armed before the program runs and hands control back within one tick.

---

the kernel "supervises nothing, configures everything"

---

5. OS services:
user interface (command line / graphical / touch), program execution, I/O, file system,
communication, error detection / resource allocation / logging / protection & security

Problems:

EXP 1.1
One program, three moments:
A = reading "hello" from the keyboard,
B = loading the program into memory,
C = executing and printing to the screen.

1. What role does the OS play in A? Which operations run on the CPU, and who wrote most of them?

the keyboard controller holds the keystrokes. the OS's keyboard DRIVER collects them (interrupt handler),
and the kernel copies the bytes to the program when it calls read().
the program itself runs only a few instructions to make the request.
almost all the CPU work (driver, interrupt handling, copying the bytes) is KERNEL code
-> written by the OS developers, not by you.

2. Why is the disk not used in A?

nothing in the request involves stored data. the characters travel from the keyboard controller to memory.
(e.g. typing in a shell: nothing is written to disk)

3. Is the CPU involved in starting B? If so, what does it run?

yes. the disk controller does the actual transfer, but the CPU runs KERNEL code that:
- finds the file
- works out which blocks to fetch
- sets up memory (page table) for the new program
- tells the disk controller what to do
(the MMU does NOT load anything -- it only translates addresses when memory is accessed)

4. Why is the disk not used in C? Could another program be using it at the same time?

printing goes to the display, not to storage.
yes, another program can use the disk at the same time -- the CPU configures the disk, lets it work,
and only gets interrupted when it is done.

5. Could hello itself use the disk, under some condition?

yes, if memory is short: the kernel may write some of hello's pages out to the disk and bring them back
when touched (swapping / paging, L08). the program never asks for this; it happens around it.

EXP 1.2 Smartphone OS: (prof: no single right answer, these are the points a good answer weighs)

1. Which desktop services would you remove, and what breaks if you do?

remove: command-line shell for users, multiple simultaneous users, general file-system browsing.
-> saves space and closes attack surface, but developers lose debugging access.
BUT protection between apps cannot go: apps are mutually distrusting "users".

2. How do you keep response times acceptable?

give the foreground app and the touch + graphics path priority over background work,
short time slices for interactive tasks, suspend / throttle background apps,
never block the UI on storage or network.
-> responsiveness is a scheduling problem first (L05).
e.g. a 60 Hz screen = a frame deadline every 1/60 s that must be met.

3. What are the unique challenges of touch, from the OS side?

touch input is continuous and must be handled at a steady rate with low latency, or scrolling stutters.
the OS must deliver input events and meet frame deadlines on time,
on a small battery budget that pushes the other way.

Bonus (prof's notes, Your turn 1.2 / 1.4 / 1.5) -- classic short-answer material

Your turn 1.2 -- privileged or not?
(a) set the timer          -> privileged: could keep the CPU forever
(b) read the clock         -> NOT privileged: knowing the time harms nobody
(c) clear memory           -> privileged if arbitrary memory (destroys others' data); clearing your own is just a loop of writes
(d) disable interrupts     -> privileged: neither timer nor devices could get the kernel back
(e) switch user -> kernel  -> can't be done directly: only by trapping, which jumps to code the kernel chose
(f) access an I/O device   -> privileged: devices are shared, one program could read others' data or wreck the disk

Your turn 1.4 -- kernel, application or library?
(a) code that picks the next program to run -> kernel (must be able to take the CPU away)
(b) printf      -> library (formats text inside your program, calls the kernel only to write)
(c) the shell   -> application (ordinary program, replaceable)
(d) disk driver -> kernel (touches a device)
(e) C compiler  -> application

Your turn 1.5 -- no mode bit: what can't the OS guarantee?
1. protection: any program can overwrite the OS / another program's memory, or reprogram a device -> one bad pointer corrupts the machine
2. getting the CPU back: any program can disable interrupts or reset the timer -> one infinite loop hangs everything
-> the "OS" is really just a library that programs agree to cooperate with
