2. Demand paging and the page fault

Demand paging means loading a page only when it's first touched.

Pure demand paging starts a process with zero pages in memory.

When a process touches a page that isn't in RAM,

its PTE says "not present" and the hardware raises a page fault, which traps to the OS. The OS then:

(1) checks that the address is legal. If it isn't, it kills the process.

(2) finds the page's location on disk.

(3) gets a free frame, evicting a page if no frame is free. That's part 2.

(4) starts the disk read. Disk is very slow, so the process sleeps and another process runs meanwhile.

(5) when the read is done, updates the PTE (frame number, valid/present).

(6) restarts the instruction that faulted. The process never knows anything happened.

---

Details:

The present bit: OSTEP's design has a separate present bit. RISC-V only has V, the valid bit. When V = 0, the OS can store the page's disk address in the rest of the PTE, and uses its own records to tell "on disk" apart from "truly invalid."

Restarting is hard for some instructions, such as auto-increment addressing or overlapping block moves that are half done when they fault. The hardware has to undo or pre-check them. RISC-V loads and stores fault precisely, so the kernel simply returns to sepc and runs the instruction again.

Free-frame list and zero-fill-on-demand: the OS keeps a list of free frames. A brand-new page gets a frame that's been filled with zeros, for security, so the process can't read the previous owner's leftover data.

---

3.  What xv6 does

xv6 does lazy allocation (demand-zero) only:

"sbrklazy" just raises p->sz, the process size, and maps nothing.

The first time the process touches the new memory, it page-faults

vmfault then checks: if va < p->sz

There's no swap and nothing is ever evicted. Pages never go to disk

fork copies all of the parent's memory eagerly.
There's no copy-on-write.

4. EAT with page faults

With p = the page-fault rate,

t_m = the memory access time and

t_f = the time to service a fault:

EAT = (1 − p) · t_m + p · t_f

Example:

t_m = 200 ns,
t_f = 8 ms,

and p = 1/1000.

8 ms = 8,000,000 ns.

EAT = 0.999 × 200 + 0.001 × 8,000,000 ≈ 200 + 8000 = 8.2 µs.

That's about 40× slower than plain memory, even though only 1 access in 1000 faults.

To stay within 10% (EAT ≤ 220 ns), you need p < 2.5 × 10⁻⁶, which is about 1 fault in 400,000 accesses.

Disk is so slow that faults have to be extremely rare.

Compare this with the TLB EAT from L07, which has the same "weighted average" shape. There a miss cost about 3× a hit; here a fault costs about 40,000× a normal access.

5. Copy-on-write (COW)

The problem it solves: fork creates a child that's a copy of the parent.

Done eagerly, as xv6 does it, that means copying every page of the parent's memory.

But most children immediately call exec, which throws all of that memory away

and loads a new program. So the copying was wasted.

The trick: don't copy yet, share, and copy only when someone writes.

after fork (COW):

parent page table frames child page table
page 0 (R only) ───────→ [ frame 5 ] ←─────── page 0 (R only)
page 1 (R only) ───────→ [ frame 8 ] ←─────── page 1 (R only)

---

(1) On fork, the OS copies only the page table, not the data. Both processes point to the "same frames", and the OS marks every page "read-only" in both tables, even pages that were writable !

(2) Reading works normally, because both processes see the same data.

(3) When one process writes, say the child writes page 1, the page is read-only, so the write traps (a page fault).

(4) The OS sees that it's a COW page.
It copies that one page into a new frame, points the child's PTE at the copy and makes it writable, then restarts the write.

=======================================

after child writes page 1:

parent page 1 ──→ [ frame 8 ] (original)
child page 1 ──→ [ frame 12 ] (copy, now writable)

page 0 still shared

Result:
only pages that are actually written ever get copied. With fork + exec, almost nothing is copied. Pages that are never written, like code, stay shared forever.

It's the same lazy idea as demand paging: don't do the work until it's actually needed.

related quetson :

Is RAM a cache for the disk?

Yes, exactly. That's the core idea of virtual memory, and locality is what makes it work.

It's the same pattern at every level, with each fast, small layer acting as a cache for the slow, big layer below it:

CPU registers
↓
CPU cache (L1/L2/L3) — caches RAM data (miss → go to RAM, ~100 ns)

TLB — caches page-table rows (miss → walk the table)

RAM — caches disk pages (miss = PAGE FAULT → go to disk, ~ms)

↓
disk (swap / files)

cache block = a page

cache miss = a page fault

eviction policy = page replacement (FIFO, LRU, clock), which is part 2

Why locality makes it work:

programs reuse the same pages (temporal locality) and touch nearby addresses (spatial locality). So a small set of pages in RAM, called the working set, covers almost all accesses, and faults stay rare.

The difference at this level: a miss is extremely expensive. A disk access is about 40,000× slower than a RAM access, while a TLB miss costs only about 3×. So:

the fault rate has to be tiny (about 1 in 400,000 to stay within 10%),

which page to evict matters much more than in the CPU cache, which is why whole algorithms exist for it in part 2,

if the working sets don't fit in RAM, locality stops helping and you get thrashing, also in part 2.

6. When there's no free frame

The OS has to evict a victim page:

If the victim is dirty (written since it was loaded), it must be written back to disk first, which is slow: two disk operations instead of one.
If it's clean, it can simply be dropped, because the copy on disk is still correct.
So, all else being equal, prefer clean victim

---

Watermarks: the OS doesn't wait until memory is completely full.

A background page daemon

wakes up when free frames drop below a low watermark (LW) and evicts pages in a batch until the count reaches a high watermark (HW).

That way a free frame is usually ready when a fault happens.

7. Replacement policies (which page to evict)

(1) FIFO

evict

the page that's been in memory longest

simple, but it can evict a page that's still heavily used

(2) OPT (optimal)

the page that won't be used for the longest time in the future

gives the fewest faults possible, but needs knowledge of the future, so it's only a benchmark

(3) LRU

the page least recently used

uses the past to predict the future (locality); usually close to OPT

8. Implementing LRU, and the clock approximation

Exact LRU is too expensive:

counters: stamp the time on every reference, then scan for the smallest when you need a victim

stack: move the page to the top on every reference.

Both mean extra work on every memory access, so real systems approximate it.

---

Clock (second chance):

each page has a reference bit, which the hardware sets to 1 whenever the page is used.

The pages sit in a circle with a "hand" pointing at one of them. To find a victim:

(1) Look at the page under the hand.

If its bit is 1: set it to 0 (the page gets a second chance), move the hand forward and look again.

If its bit is 0: this page is the victim. Put the new page there with its bit set to 1, and move the hand one step past it.

(2) If all the bits are 1, the hand goes all the way around clearing them, and ends up evicting the page it started at. That's exactly FIFO.

---

Enhanced clock:

also looks at the dirty bit, and prefers (reference 0, clean) over (reference 0, dirty), because a clean page needs no write-back.

On RISC-V, the A bit in the PTE is the reference bit and the D bit is the dirty bit. xv6 never reads them, since it never evicts.

---

Others:

LFU: evict the page used least often. It keeps counts, and shifts them right periodically so that old popularity fades.

Prefetching: when page P faults, load P + 1 as well, betting on spatial locality.

===================================

9. Thrashing

If the sum of all processes' working sets is bigger than RAM, every process keeps evicting pages another process needs.

Almost every access faults, the CPU sits idle waiting for the disk, and CPU utilization collapses.

The trap is that the OS sees a low CPU load and may admit more processes, which makes things worse.

The fixes:

admission control: run fewer processes at once, by suspending or swapping some out.

an OOM killer, which kills a process to free memory.

=======================
NOtice:

The usual LRU structure, a hash map plus a doubly linked list (the LeetCode one), is O(1) per access, so the data structure isn't the problem. The problem is who would have to update it, and how often.

1. LRU has to be updated on every memory reference. That's every load and store, billions per second. Each one moves a page to the "most recent" position.

2. The OS never sees those references

On a TLB hit, the hardware translates and accesses memory entirely by itself, with no trap and no kernel code running. The OS only gets control on a page fault, which is rare. So the OS can't keep the list up to date, because it doesn't know when pages are used.

---

What hardware can do cheaply is set one bit. When a page is accessed, the MMU sets the A (reference) bit in its PTE, and the D (dirty) bit if it was a write. That costs almost nothing.

So clock splits the work:

the hardware sets the reference bit on use (cheap, on every access),
the OS reads and clears those bits, and only when it needs a victim, on a fault (rare).
The single bit only answers "was this page used since I last checked?", not the exact order of use. That's why clock is an approximation of LRU. In practice it's close enough, and it costs almost nothing.

=========================

for the trashing . are you describing the senario like when we want to run so many prorgams on a pc it run out of ram , so it has to keep swap use disk

Yes, that's the scenario. One detail separates thrashing from normal swapping.

Normal swapping is fine. If you have many programs open but most are idle, their pages get swapped out and nobody notices. When you switch back to an idle app it's slow for a second while its pages load, and then it's fine. RAM is acting as a cache, and the cache is working.

Thrashing is when the actively used pages don't fit.

The programs that are running right now together need more RAM than you have. That's the sum of their working sets. Then:

1. Program A faults and evicts a page that B is using.

2. B runs, faults, and evicts a page that A is using.

3. Everyone is waiting on the disk all the time, and almost no real work gets done.

What it looks like on a PC:

the whole machine freezes or stutters, the mouse lags, the disk is constantly busy, and Task Manager shows memory at about 100%.

For example, an 8 GB laptop with a game, 50 Chrome tabs and a video editor all active at once.

Why it's a trap: CPU utilization drops, because every process is waiting on the disk. An older OS scheduler might read that as "the CPU is idle, let's start more processes," which makes it even worse.

The fixes:

Admission control: run fewer things at once. On a PC, that means you close apps; the OS can also suspend processes.
OOM killer (out-of-memory killer): Linux kills a process to free memory.

Or add more RAM, so the working sets fit.

EXP 8.1: EAT

1. Memory takes 200 ns and a fault takes 8 ms. What's the EAT when 1 in 1000 accesses faults? What fault rate keeps the slowdown within 10%?

For 200 ns memory access (page is there), a fault takes 8 ms = 8,000,000 ns (page not there).

EAT = (1 − p) · (time when it's there) + p · (time when it's not there)

**When 1 in 1000 faults (p = 0.001):**

EAT = 0.999 × 200 + 0.001 × 8,000,000 = 199.8 + 8000 = **8199.8 ns ≈ 8.2 µs**, about **41× slower** than plain memory (8200 / 200).

**Within 10% slowdown:**

10% of 200 is 20, so the max EAT is 200 + 20 = **220 ns** (not 210).

220 = (1 − p) × 200 + p × 8,000,000
220 = 200 − 200p + 8,000,000p
20 = 7,999,800 p
p ≈ 20 / 8,000,000 = **2.5 × 10⁻⁶**, i.e. about **1 fault in 400,000 accesses**.

(Solve for p, the fault rate, directly. Writing x for the hit rate also works, but then the answer is 1 − x.)

**2. OSTEP's formula, AMAT = T_M + P_miss · T_D, memory 100 ns, disk 10 ms. AMAT at hit rates 90% and 99.9%?**

T_D = 10 ms = 10,000,000 ns. P_miss = 1 − hit rate (multiply the disk time by the MISS rate, not the hit rate).

- Hit rate 90% → P_miss = 0.1: AMAT = 100 + 0.1 × 10,000,000 = 100 + 1,000,000 = **1,000,100 ns ≈ 1 ms**
- Hit rate 99.9% → P_miss = 0.001: AMAT = 100 + 0.001 × 10,000,000 = 100 + 10,000 = **10,100 ns ≈ 10.1 µs**

Even at 99.9% hits, memory is about 100× slower than with no misses. Disk dominates.
Difference from the EAT formula: AMAT always pays T_M (even a miss reads memory after the disk), so there's no (1 − p) in front of T_M.

**3. A fault takes 8 ms with a free frame or a clean victim, and 20 ms when the victim is dirty (70% of the time). Memory 100 ns. What fault rate keeps EAT ≤ 200 ns?**

Average fault time = 0.3 × 8 + 0.7 × 20 = 2.4 + 14 = **16.4 ms = 16,400,000 ns**.

200 = (1 − p) × 100 + p × 16,400,000
200 = 100 − 100p + 16,400,000p
100 = 16,399,900 p (16,400,000 − 100, not + 100)
p = 100 / 16,399,900 ≈ **6.1 × 10⁻⁶**, i.e. about **1 fault in 164,000 accesses**.

Watch the zeros: 16.4 ms = 16,400,000 ns (7 digits after the 16.4 → ×10⁶).

**1. A, B, C, D with bits 1, 0, 1, 1, hand at A. Who is evicted, what are the bits after (new page gets bit 1), where does the hand stop?**

```
        A(1)  ← hand
   D(1)      B(0)
        C(1)
```

- Hand at A: bit 1 → clear to 0, move to B.
- Hand at B: bit 0 → **B is evicted**. New page (call it E) goes into B's slot with bit 1. Hand moves past it to C.

```
        A(0)
   D(1)      E(1)
        C(1)  ← hand
```

Bits after: A 0, E 1, C 1, D 1. **Hand stops at C.** (C and D were never looked at, so their bits stay 1.)

**2. All bits 1, hand at A. Who is evicted, and which policy did clock act like?**

- A: 1 → 0, move on. B: 1 → 0. C: 1 → 0. D: 1 → 0. Back at A, now 0 → **A is evicted**.
- New page goes in A's slot with bit 1, hand moves to B. B, C, D are left with bit 0.

The hand went all the way round clearing every bit, then evicted the page it started at, which is just the next one in circular (arrival) order. So clock acted like **FIFO**. Clock only beats FIFO when some bits are 0; if every page was used recently, it has no information to choose with.

**3. B and C both have bit 0. B is dirty, C is clean. Which goes, and why?**

**C (the clean one)**, under the enhanced clock, which looks at (reference bit, dirty bit) and prefers (0, clean) first.

Why: a clean page can just be dropped, because its copy on disk is still correct. A dirty page must be written back to disk first, which is a second slow disk operation (the 8 ms vs 20 ms in EXP 8.1 part 3). Both were equally "not recently used", so pick the cheaper one.

(Basic clock, which ignores the dirty bit, would just take whichever one the hand reaches first.)
