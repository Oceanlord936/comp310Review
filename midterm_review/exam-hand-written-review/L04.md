2. fork() : one call , two return

Afterwards there are two processes running the same program at the same instruction, each with its own copy of memory. They tell themselves apart by the return value:

child gets 0
parent gets the child's PID

In xv6 the whole trick is one line in

kfork: np->trapframe->a0 = 0;

The child's copy of a0, the return-value register, is set to 0. The parent's a0 gets the PID normally.

---

Why give the PID to the parent???

A parent may have many children.
The PID is the only way to refer to one later, to wait for it or kill it.

If both got 0, neither would know its role.

Why 0 is safe for the child: no process ever has PID 0 (init is PID 1).

How the child finds PIDs: it calls getpid() for its own.
Linux has getppid() for the parent's;

xv6 has no such call, so a child that needs it must be given it before the fork.

---

Counting: n sequential forks → 2ⁿ processes.

Nested (the second fork only in the child's branch) → 3.

Fork copies; it doesn't share. x = 5 before the fork, the child does x++ → the child sees 6, the parent still sees 5.

Why two calls instead of one:

between fork and exec, the child runs your code in the new process. That's where the shell sets up the child's world with ordinary syscalls: close a file and open another to redirect output, connect a pipe, change directory. A single "create a process running X" call would need a parameter for every option.

4. The shell in four calls

int pid = fork();
if (pid == 0) {
exec("/bin/ls", argv); // child: become ls

}

5. Termination

exit() asks the OS to delete the process.
Its status goes to the parent, which collects it with wait().

When resources are reclaimed differs by OS:

Linux: frees the memory immediately, inside exit. Only a small record with the exit status remains.

xv6: exit closes files and gives the children to init, but keeps the memory. freeproc frees the memory and page table later, when the parent's wait collects the child.

kill in xv6 only sets p->killed. The victim notices and calls exit itself the next time it heads back to user space.

---

Zombie: the child has exited and the parent hasn't called wait.

Its table slot, PID and exit status stay until they're collected. It uses no CPU.

Leaked zombies fill the table: on xv6 they hold some of the 64 slots, and on Linux they hold PIDs that can't be reused. Eventually nothing new can start.

---

Orphan: the parent exits first, leaving a running child.
The kernel re-parents it to init (reparent() scans proc[] and sets parent = initproc), and init waits on it.

That's why init() spends its whole life in a wait loop. Some systems use cascading termination instead, killing the children.

---

Notice:

kill doesn't remove a process. It makes it exit, and then it sits as a zombie until its parent waits. No signal can remove a zombie, because it's already dead. The fix is in the parent.

=============================

6. Isolation and address spaces

Each process has its own page table, so no address it can generate names another process's memory.

Isolation costs nothing at run time: the hardware simply can't resolve the reference.

---

Something must be shared to enter the kernel at all:

Linux maps the kernel into the top of every address space, protected from user mode.

xv6 keeps a separate kernel page table and maps only the "trampoline" and the process's "trapframe" into each process.

---

Every process switch is an address-space switch:

one write to 'satp' , done in the trampoline.

On the way in it installs the kernel's table; on the way out, the process's own. Changing satp invalidates cached translations, which is why the TLB matters (L07).

(d) why return the child's PID to the parent rather than 0 to both?

a parent may have many children, and the only way to refer to a particular one later -- to wait() for it
or kill() it -- is by its PID. nothing else tells the parent which process it just made.
if both got 0, neither could tell which role it had (which branch to take).

EXP 4.2

(a) why does an address-space switch happen with every process switch?

because the address space is PART OF THE PROCESS. the incoming process's addresses mean nothing under the
outgoing process's page table, so the translation (satp) must change before the incoming process runs a
single instruction.

(b) two processes both read 0x1000 -- same byte?

not in general. each reads 0x1000 in ITS OWN address space, and each page table maps it to a different
physical frame. they see the same byte only if the kernel deliberately mapped both to the same frame
(read-only shared code, shared memory).

(c) a zombie -- does it still have an address space? xv6 and Linux.

xv6: YES. exit does NOT free the page table or the user memory; the parent's wait does, through freeproc.
Linux: NO. the memory is released during exit; only the task record with the exit status remains.
(that's what "a zombie could be more than a number" means)

(d) if isolation is enforced by hardware, why does the kernel need to be involved?

the hardware enforces whatever page tables it is GIVEN -- but someone has to BUILD them: decide which frames
each process gets, fill in the entries, load the right table (satp) on each switch, and handle the faults.
the hardware checks every access; the kernel decides what the rules are.

Bonus (prof's notes)

Your turn 4.2 -- why is cd built into the shell?
the current directory is part of the PROCESS (cwd in struct proc).
if cd were a program: the shell forks a child, the child execs cd, which calls chdir and changes the
CHILD's directory, then exits. the shell's own directory is unchanged -> the next command runs in the old place.
so the shell must call chdir in its OWN process, without forking. xv6's sh.c does exactly that, as a special
case at the top of its main loop.

Your turn 4.4 -- how many lines of output?
for (i = 0; i < 3; i++) fork();  printf("hi\n");
-> each iteration doubles the processes: 2^3 = 8, so "hi" is printed 8 times.
with printf("start ") (no newline) before the loop, on Linux, output to a file:
the C library BUFFERS output to a file and flushes at exit. "start " is still in the buffer -- in the
process's memory -- when the first fork copies that memory. every process inherits a copy of the unflushed
buffer and writes it at exit -> "start" appears 8 times.
can't happen on xv6: its printf writes each character immediately.
fix on Linux: fflush(stdout) before forking.

Your turn 4.5 -- exit before wait
at exit the child becomes ZOMBIE and the kernel wakes the parent (in case it's sleeping in wait); the parent
isn't waiting, so nothing else happens. the zombie stays in the table, still holding its memory (xv6).
when the parent finally calls wait: the kernel finds the zombie immediately WITHOUT sleeping, copies out its
exit status, frees it with freeproc (slot -> UNUSED), and returns its PID.
no children at all: wait returns -1 at once (nothing it could ever wait for).
