Round 2: L02, Traps (System Calls, Interrupts, Faults)

=============================

1. One mechanism, three causes

-system call
caused by a deliberate ecall
it is SYNCHRONOUS (happens exactly at the ecall)
it resumes AFTER the ecall

---

-interrupt
caused by something external: timer or a device
it is ASYNC, resumes ON the interrupted instruction
(that instruction never ran)

---

-exception
accidental: bad address, illegal instruction
it is SYNC
if it gets fixed -> re-run it
if illegal -> killed

---

what the hardware does on every trap?

1. saves the PC (program counter) in "sepc"
2. records the cause in "scause"
   (also stval: extra info such as the faulting address)
3. switches to kernel mode, and to a stack the program cannot reach
4. jumps to the one fixed entry point the kernel chose at boot ("stvec")

so in short:
save PC in "sepc", save the cause in "scause", switch the CPU into kernel mode, jump to the one fixed entry point the kernel chose ("stvec")

Notice! the program does NOT choose the destination. that is the entire security argument

=====================================

2. System calls: the service interface

4 calls:
open(), read(), write(), exit()
are enough to write a 'cp' program. every call can fail, and returns a value saying so (-1)

---

read() returning fewer bytes than asked for is NOT an error
(a pipe, a terminal, end of file all legitimately give short reads)

Dispatch: the "library stub" puts the syscall number in a7 and executes 'ecall'
(always a7 in xv6)

the kernel then calls
syscalls[a7]() , and the result goes in a0

---

Notice: syscalls are called by NUMBER, NOT by name or address:

the kernel's addresses are not the program's business, and the program must not pick where to enter

---

Passing arguments, HOW ???

three ways

1. registers (fast, but few. xv6 uses a0 - a5, 6 of them)

2. a block of memory (pass its address in a register; no limit on number/size)

3. the stack (program pushes, kernel pops)

---

notice: the kernel never trusts a user pointer.
it copies through the process's page table instead!
(copyin / copyout / argstr), which fails safely if the address is invalid

---

A library function is NOT a syscall.
"printf" formats and buffers inside your program. the syscall underneath is write().
xv6's printf makes one write PER CHARACTER
-> printf("hello\n") = 6 syscalls (1 with a buffering libc)

"strlen" and "memcpy" never enter the kernel at all (that's why they're fast)

---

six families of syscalls:

-process control:          fork() , exec() , exit() , wait() , kill()
-file management:          open() , read() , write() , close() , fstat()
-device management:        mknod() , dup()
-information maintenance:  getpid() , uptime()
-communication:            pipe()
-protection:               chdir() , link() , unlink()

Notice: xv6 has 22 built-in syscalls
new ones we add start at 23

===========================

3. Interrupts: the uninvited trap

the interrupt cycle:

1. the device raises its line. the CPU notices after the current instruction
2. the CPU saves state, reads the cause, jumps to the kernel
3. the handler services the device (copies data, wakes waiters)
4. the handler acknowledges the interrupt (so the device can raise it again)
5. state is restored and the program resumes, unaware

---

Interrupt-driven I/O: the CPU is involved in every block.

DMA: direct memory access
the CPU sets up the buffer address, count and command ONCE, the controller copies everything itself.
there is ONE interrupt at the end.

---

without interrupts there is no OS:

the timer is how the kernel takes the CPU back from a program that never asks for anything.
disabling interrupts is privileged

---

GINI slows the timer to about 2 ticks / sec
(stock xv6 under QEMU is about 10 / sec)

on an idle machine, only the timer bucket grows

===========================================

4. Exceptions: a fault is not an error

scause values:

exceptions:
8  = ecall from user
12 = instruction page fault
13 = load page fault
15 = store page fault
2  = illegal instruction

---

interrupts (top bit set):
5 = supervisor timer
9 = external device

---

four reasons for a page fault, and only ONE is fatal:

1. lazy allocation:  fault -> allocate -> retry
2. copy on write:    write to a shared read-only page -> private copy -> retry
3. stack growth:     extend -> retry
4. illegal access:   kill

xv6 implements only lazy allocation
-> (sbrklazy)

---

## "usertrap()": here is the shape

// save the PC into the trapframe
p->trapframe->epc = r_sepc();

// 8 = ecall from user = syscall
if(r_scause() == 8){

    // move PC +4 to the next instruction
    // we want to return to the instruction AFTER the ecall
    p->trapframe->epc += 4;
    intr_on();
    syscall();

}
else if ((which_dev = devintr()) != 0) {
    // timer / device
}
else if ((r_scause() == 15 || r_scause() == 13) && vmfault(...) != 0 ){

    // lazily allocated page: fixed, retry
    // (epc NOT advanced)

}
else{
    // not syscall, not interrupt, not a fixable lazy fault
    // this is fatal!
    setkilled(p);
}

// timer: give up the CPU
if(which_dev == 2) {
    yield();
}

---

Why epc += 4 only for syscalls: a syscall must not repeat;
a fixed fault must re-run the instruction.

vmfault decides with one comparison, va >= p->sz. "The page table records what the kernel has done;
p->sz records what it agreed to."

xv6 NULL pointer quirk: page 0 holds the program's own code. A read through NULL doesn't fault (it returns code bytes). A write gets scause 15 with stval 0 -> killed. Linux leaves page 0 unmapped, so both fault.

Questions:

EXP 2.1 In this cp, the program never checks what open() returned:

---

// sfd = source fd, dfd = destination fd
// argv[1], argv[2] = the two file names (argv[0] is the program name)

int sfd = open(argv[1], O_RDONLY);
int dfd = open(argv[2], O_CREAT|O_WRONLY);

// read() returns how many bytes it got; keep going while > 0

while ((n = read(sfd, buf, sizeof(buf))) > 0){
    if (write(dfd, buf, n) != n) { (void)write(2, msg, sizeof(msg)); exit(EXIT_FAILURE); }
}

return EXIT_SUCCESS;

---

1. If an open() fails, does it crash or keep running?

NO crash. a failed open() returns -1, and the program carries on using -1 as a file descriptor.

(a) source fails: read(-1, ...) also fails, returns -1 -> loop condition false, loop never runs
    -> main returns EXIT_SUCCESS. it REPORTS SUCCESS having copied nothing,
    and it already created / emptied the destination file. that is WORSE than a crash.

(b) destination fails: the first read succeeds, then write(-1, ...) returns -1, which is != n
    -> prints the error and exits, but the message can't say what really went wrong,
    because the failure happened two calls earlier.

2. If it fails, where exactly, and why there rather than at the open()?

with raw syscalls, nothing crashes (see above). a crash appears only once POINTERS are involved:
with the C library's fopen, failure returns NULL, and the program dies later inside fread,
far from the real cause -- because the bad value is only used later, not at the open.

3. What's the advantage of checking at the open() and exiting immediately?

you report the TRUE reason (perror can print it) at the moment it happens,
BEFORE any side effects (like creating/emptying the destination file).

EXP 2.2 (when should something be a system call?)

(a) why must creating a file go through the kernel?
the file system is shared by every program and user: someone must check permissions, allocate space,
and keep the on-disk structures consistent -- a program can't be trusted with that.
also the disk is a device, reachable only in kernel mode.

(b) why is using the GPU not a syscall per operation?
a computation sends millions of small operations; a trap costs far more than one GPU command,
so trapping for each would waste most of the time in kernel entries.
instead the kernel sets up access ONCE (maps the device's memory/command queues into the process),
and the app submits work in large batches.

(c) where is the code that actually performs a read()?
in the kernel: the file-system code and the disk driver, running in kernel mode on the process's behalf.

(d) why can't an app reimplement read and skip the call? faster?
it can't reach the device: the disk controller is not on its page table and the instructions are privileged.
even if it could, every program would carry its own file system copy and they'd corrupt each other's data.
it might save the trap cost, but the kernel's shared buffer cache often makes the kernel path faster anyway
(a block already in memory needs no disk access).

EXP 2.3 A 1 MB file is 1024 blocks.

Interrupt-driven: per block, the controller takes 300 µs to fetch (the CPU is free meanwhile), then the CPU spends 50 µs copying the block to memory.
DMA: 500 µs of CPU setup, then a 1500 µs transfer with no CPU.
For each: what is the total transfer time, and how much CPU time goes to the transfer?

---

interrupt-driven:
total = (300 + 50) x 1024 = 358,400 µs ≈ 358 ms
CPU busy = 50 x 1024 = 51,200 µs ≈ 51 ms, in 1024 separate interruptions

DMA:
total = 500 + 1500 = 2,000 µs = 2 ms
CPU busy = 500 µs = 0.5 ms, all at the start

-> DMA is ~180x faster overall and uses ~1/100 of the CPU time.
bigger gain: 1024 interrupts (each saving/restoring state) became ONE.

EXP 2.4 Apps are allowed to disable interrupts.

1. What breaks, beyond the timer?
(immediate one: the timer can't take the CPU back -> a loop with interrupts off owns the machine forever)
also:
- device data is LOST when buffers overflow unserviced (keystrokes, network packets)
- the clock stops advancing
- I/O completions never wake anyone -> every waiting process stays blocked

2. Does it hurt the offender itself, or only others?
BOTH. the program itself may be waiting for I/O that can now never complete (it can deadlock itself).
but mostly it's everyone else who suffers.

3. Is there any legitimate reason for the kernel to disable interrupts, and for how long?
YES: to protect a SHORT piece of kernel code that shares data with an interrupt handler,
so the handler can't run in the middle of an update.
it must be BRIEF -- a few instructions -- or the kernel creates the same problems for itself.
xv6 turns interrupts off while holding a spinlock for exactly this reason (L09/L10).

EXP 2.5 Classify each:

(a) write()
SYSCALL, SYNCHRONOUS -- happens exactly at the ecall, scause 8.
(a syscall is never async: you asked for it at a known instruction)

(b) a NULL-pointer read on Linux: what's in stval?
EXCEPTION, synchronous: a load page fault, scause 13, stval = 0 (the faulting address).
(on xv6 the read would NOT fault -- page 0 is the program's own code)

(c) the timer firing in a tight loop: what may the kernel do next?
INTERRUPT, ASYNC: scause has the top bit set, code 5.
the kernel may SWITCH TO ANOTHER PROCESS -- exactly what usertrap does with yield().
(it only comes back to the same process if nothing else is runnable)

(d) jumping into code not yet loaded: has anything gone wrong?
EXCEPTION, synchronous: an instruction page fault, scause 12.
NOTHING has gone wrong in a system that loads code on demand: the kernel reads the page in and retries.
(stock xv6 loads the whole program at exec and doesn't handle scause 12, so there it would be fatal)

(e) Which can happen at an instruction the program didn't choose, and why is that the hardest to handle?
ONLY THE INTERRUPT. syscalls and exceptions happen at a known instruction, but an interrupt can arrive
between ANY two instructions -- including in the middle of an update to shared data.
so kernel code that an interrupt handler might also touch must be written as if it could be paused at
every point -> the root of L09/L10 (synchronization).

Bonus (prof's notes)

Your turn 2.4 -- why not just jal to sys_open?
1. a jump does NOT change the mode bit -> kernel code would run in user mode, and every privileged
   instruction it uses would trap.
2. even if it could switch modes, it would let the program CHOOSE where to enter the kernel
   (e.g. just after a permission check). ecall switches mode AND forces entry at the one address the
   kernel registered at boot (stvec), so every call passes the kernel's checks.

Your turn 2.5 -- 20-char printf, 2 timer ticks, 3 lazy faults on xv6: how many kernel entries?
syscall bucket: 20 writes (one per char) + 1 exit = 21
timer bucket: 2
page-fault bucket: 3
total = 26 (plus any start-up calls and console device interrupts)
with a buffering libc the syscall bucket would be 2, not 21.
