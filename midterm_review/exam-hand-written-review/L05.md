===================================== 3. Five criteria

CPU utilization ↑, throughput ↑ (jobs completed per unit of time)

Turnaround ↓ = finish − arrival

Waiting ↓ = total time in the ready queue = turnaround − burst

Response ↓ = first run − arrival

---

These criteria conflict, so a scheduler is really a ranking of them ("the ranking is the design").

======================================

4. FCFS (first come , first serve)

FIFO and non-preemptive. Results depend heavily on arrival order.

Bursts 24, 3, 3:

order P1, P2, P3: waits 0, 24, 27,
so the average is 17 ms

order P2, P3, P1: waits 0, 3, 6,
so the average is 3 ms

Convoy effect: one CPU-bound job holds the CPU while all the I/O-bound jobs line up behind it, and the I/O devices sit idle.

===================================

5. SJF (shortest next CPU burst first)

Bursts 6, 8, 7, 3

SJF averages 7 ms, FCFS averages 10.25 ms.

Provably optimal for average waiting time.
Swap argument:

if a longer job L runs right before a shorter job S, swap them. S's wait drops by L and L's wait rises by S, so the total changes by S − L < 0. Repeat the swaps (bubble sort) until the order is shortest-first.

Impossible to implement: it needs the length of the next burst, which is in the future.

=====================================

6. Predicting the burst: exponential averaging

τₙ₊₁ = α·tₙ + (1−α)·τₙ

tₙ = the burst just measured
τₙ = what was predicted for that burst

α = 0 ignores the measurement;
α = 1 ignores the history;

α = ½ is the usual choice.

Unrolled, every past burst counts, with geometrically shrinking weights. It costs one multiply and one add, and stores one number.

==================================

7. SRTN (preemptive SJF, also called STCF)
   -> shrotest remain

On every arrival, compare the newcomer's burst with the running job's remaining time.

Arrivals 0, 1, 2, 3 with bursts 8, 4, 9, 5:

the average wait is 6.5 ms.
P2 arrives at 1 needing 4,
which is less than P1's remaining 7 (8 - 1 = 7),
so P2 preempts.

Costs: more context switches, and starvation of long jobs.

======================================

8. Round Robin (★ this is what xv6 runs)

FCFS plus a timer: each process runs
for at most a quantum q,
then goes to the back of the queue.

With n processes, each gets 1/n of the CPU and waits at most (n−1)q.

Bursts 24, 3, 3 with q = 4: the average wait is 5.66 ms. That's worse than SJF, but nobody gets stuck behind a long job.

Choosing q (the time quantum before switch ):

q too small: it's responsive, but drowns in context switches.

q too big: it degenerates into FCFS.

Rule of thumb: make q longer than most bursts, so most processes block on their own before being preempted.

xv6: the quantum is 1 timer tick. The timer interrupt makes usertrap call yield, and the scheduler continues its scan of proc[], wrapping around at the end.

=================================

9. Priority scheduling

The highest priority runs; ties are broken FCFS. Low number = high priority usually, but check the question.

SJF is just priority scheduling where the priority is the predicted burst.

Starvation: a low-priority process may never run. The fix is aging: raise a process's priority gradually while it waits.

====================================

10. Turnaround vs. response: no ordering wins both

Three 5 s jobs:

RR, q = 1: responses 0, 1, 2 (average 1 s); finishes at 13, 14, 15 (average turnaround 14 s)

SJF: responses 0, 5, 10 (average 5 s); turnaround 10 s

Batch-style scheduling wins on turnaround; RR wins on response.

11. Proportional share: state the ratio first

Lottery:

each slice is a lottery, and a client holding t of the T tickets wins with probability t/T. Draw a number in
[0, T), then walk the list adding up tickets until the running sum is greater than the draw.

Fair on average,
not in the short run.

Example: with A at 75 tickets and B at 25, over 20 slices there's about a 41% chance B wins 4 or fewer slices.

Fairness metric F = (finish time of the first job) / (finish time of the second), for two identical jobs. F = 1 is perfect.

Ticket mechanisms:
Currency: a user splits their share in their own units, and the system converts those to global tickets.

Transfer: lend your tickets to the process you're waiting on (for example, a server doing work for you).
Inflation: a process mints its own tickets. This is safe only among processes that trust each other.

---

Stride: stride = (big constant) / tickets, and every pass value starts at 0. Each quantum, run the client with the smallest pass, then add its stride to its pass.

It's deterministic: the exact ratio comes out every cycle.

New problem: what pass should a newcomer start with? If it starts at 0, it monopolises the CPU.

Prof's example:

A/B/C hold 100/50/250 tickets

with W = 10000,
so the strides are 100/200/40.

The run order is A B C C C A C C.

After 8 quanta the counts are C 5, A 2, B 1,

which is 250 : 100 : 50.

Notice: there's no rand in the kernel. You write your own generator (xorshift or an LCG) seeded from something like ticks. Xorshift seeded with 0 returns 0 forever.

SRTN

he trick is a small table of remaining times, updated at every decision point. A decision point is any arrival or any finish.

Rules:

At each decision point, run the job with the least remaining time.
On a tie, the running job keeps the CPU. Among jobs that are waiting, the earlier arrival wins (FCFS).
