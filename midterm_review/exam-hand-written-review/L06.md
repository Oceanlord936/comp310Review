# Round 6: L06 Memory Management

---

## 1. Why the hardware has to check addresses

The CPU can only directly reach registers and main memory. Memory just receives an address and returns data.

It has no idea which process is asking. So the hardware has to block illegal accesses before they reach memory, on every single access.

Software is far too slow to check each load and store.

---

## 2. Base + limit registers (addresses are physical)

An address is legal if:

`base <= addr < base + limit`

Otherwise the CPU traps to the OS, and the process usually gets killed. That check takes **two comparisons**.

The OS reloads base and limit on every context switch, because each process has its own region.

Loading them is **privileged**. If a user process could set its own base and limit, it could read or write anyone's memory.

xv6 does not use base + limit. Its page table does the same job **page by page**.

---

## 3. Address binding: when does an address become a real physical address?

1. **Compile time**
   - absolute addresses are baked into the code
   - program cannot move after it starts
   - e.g. xv6 kernel linked at 0x80000000

2. **Load time**
   - relocatable code; the loader patches the addresses once
   - program cannot move after it starts
   - e.g. a loader that fixes up addresses before start

3. **Execution time**
   - translated on every access by hardware (the MMU)
   - can move after it starts running
   - enables swapping, paging, virtual memory

---

## 4. Logical vs physical address, and the MMU

With execution-time binding there are two kinds of address:

- **logical (virtual)**: what the CPU generates
- **physical**: what memory sees

The MMU (memory management unit) translates logical → physical. This happens in hardware, on every access.

Every xv6 user program is linked to start at logical address 0. Two programs cannot both live at physical 0, so the MMU is not optional.

### Barebones MMU: relocation register + limit register

```c
if (la >= limit) trap;   // addressing error
pa = la + reloc;
```

A has 1000 bytes at physical 14000 (reloc 14000, limit 1000):

- logical 346 → 346 < 1000 ✓ → physical **14346**
- logical 1000 → not < 1000 → **trap**

Logical addresses start at 0, so the lower comparison from "base + limit" is gone:
**1 comparison + 1 addition** (base + limit was 2 comparisons).

The program never sees 14000.

### Worked example: base 16384 (16 KB), bounds 4096 (4 KB)

| virtual | check < 4096 | physical |
|---|---|---|
| 0 | ✓ | **16384** (the base itself) |
| 1024 | ✓ | 16384 + 1024 = **17408** |
| 3000 | ✓ | 16384 + 3000 = **19384** |
| 4400 | ✗ | **fault** |

Bounds can hold the size (check, then add) or the physical end (add, then check). The protection is the same.

Waste: the whole 4 KB slot is reserved, but heap + stack use only part of it.
The gap between them is lost inside the allocation (L07 removes this).

## Problems

### EXP 6.1: When are addresses bound in each case?

**(a) The xv6 kernel is linked at 0x80000000, and QEMU loads it exactly there.**

**Compile-time binding.** The address written in the code is the actual place in physical memory.

1. When the kernel is built, the linker fixes every address in it, starting at 0x80000000, so the final addresses are already baked into the binary.
2. QEMU loads the kernel at exactly 0x80000000.
3. Every address in the code is therefore already correct. The loader doesn't patch anything, and the hardware doesn't translate anything.
4. The kernel can't move. If it were loaded anywhere else, every address in it would be wrong.

Extra fact: xv6 does turn on paging later, but it maps the kernel so that virtual address = physical address. So the kernel's addresses still mean the same place after paging is on.

**(b) A loader places a program and adjusts every address before it starts.**

**Load time**, and the program cannot move once it is running.

Why it cannot move: the loader patches each address once, turning it into a real physical address. After that, the program behaves as if it had been compiled for that exact location. If the OS moved it:

- every patched address in the code would point to the old location, and
- worse, the running program has already made new pointers of its own, stored in variables, on the stack and on the heap. The OS can't find all of those to fix them.

So the program stays where the loader put it.

Compared with compile time: at compile time the location is fixed before the program ever runs, so it can only run at that one place. With load time, the location is chosen when the program starts, so it can be loaded anywhere free. Once it's running, though, it's stuck there. That extra flexibility at start-up is what load time gains.

**(c) A program is swapped out, then brought back into a different region.**

**Execution-time binding.**

1. It comes back to a **different** place, not the same place. "Swapped out" means:
   - The OS copies the process's memory to disk and frees that RAM.
   - Later the OS brings the process back in, into whatever region happens to be free. That's usually a different physical location from before.

   If the process were always guaranteed to come back to the same place, load-time binding would have been enough. The whole difficulty is that it comes back somewhere else.

2. The OS moves it, and the MMU makes the move work. The two jobs are separate:
   - **OS**: copies the process into the new region, then sets the relocation register to the new base.
   - **MMU**: translates on every access: `pa = la + relocation`.

   The code never changes, because every address in it is logical and starts at 0. Only the register value is different.

About "allocate more": that's a separate idea, a process growing (for example its heap). With relocation + limit, growing means the OS raises the limit register, provided there's free space right after the process (EXP 6.2 part 2).

About states: a swapped-out process isn't simply "waiting" or "ready". It's **suspended**, with its memory on disk. It can't run until it's swapped back into RAM.

**(d) Which of these can move after it starts, and what does it need from the hardware?**

Only (c), execution-time binding, can move after it starts.
It needs an **MMU**: hardware that translates EVERY access (limit check, then `pa = la + relocation`).

Split of jobs: the OS sets the relocation + limit registers (privileged, on each switch / move); the MMU does the translation by itself on every load/store. The OS is not involved per access (too slow).

(a) and (b) can't move: their addresses are already physical once the program runs.

### EXP 6.2: base = 32768 (32 KB), bounds = 2048 (2 KB)

**1. Translate the virtual addresses 0, 1000, 2047, 2048 and 5000, or say "fault".**

Check the bound first, then add the base.

| virtual | check va < 2048 | physical = 32768 + va |
|---|---|---|
| 0 | ✓ | 32768 + 0 = **32768** |
| 1000 | ✓ | 32768 + 1000 = **33768** |
| 2047 | ✓ | 32768 + 2047 = **34815** (last legal byte) |
| 2048 | ✗ | **fault** (bounds = size, so legal is 0 … 2047) |
| 5000 | ✗ | **fault** |

Trap: virtual 0 → the base itself (32768), don't add the bounds.
Always write the final number, not just "32768 + 1000".

**2. The heap grows so the process needs 3000 bytes. Which register changes, and to what?**

The **bounds (limit)** register changes from 2048 to **3000**. The base stays at 32768.

- Bounds is the size of the process's memory, and the MMU's check is `va < bounds`.
- If bounds stayed at 2048, any heap access from 2048 to 2999 would fault.
- Raising bounds to 3000 makes virtual 0 … 2999 legal, which is physical 32768 … 35767.
- The base doesn't change, because the process hasn't moved. It has only grown at the end.

Catch: this only works if physical memory right after the process (up to 35767) is free. If another process is sitting there, the OS has to move this process somewhere bigger first (part 3).

(Not the trapframe. That's xv6 paging, L07. Base + bounds has only the two registers.)

**3. The OS moves the process to physical 48 KB. What changes in the code, and what changes in the registers?**

Only the **base** register changes. The code doesn't change at all.

| | before | after |
|---|---|---|
| code | logical addresses from 0 | **unchanged** |
| base | 32768 (32 KB) | **49152** (48 KB = 48 × 1024) |
| bounds | 3000 | **3000** (same size) |

Steps: the OS copies the 3000 bytes from 32768 to 49152, then sets base = 49152 (privileged).

Check: virtual 1000 → before 33768, after 49152 + 1000 = **50152**. Same logical address, new physical byte.

Rule: **base** changes when the process **moves** (where it starts). **Bounds** changes when it **grows or shrinks** (how big).
