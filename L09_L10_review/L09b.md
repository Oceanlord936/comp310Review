11. Memory barriers (when stores become visible)

9a ended with this problem: the compiler or the CPU may reorder loads and stores to different variables, and that breaks Peterson.

The "memory model" is the CPU's rule for when a store by one CPU becomes visible to the other CPUs:

---

strongly ordered: a store is visible to every CPU at once, in program order.

weakly ordered: it may not be. Other CPUs can see stores late, or in a different order. Most modern CPUs (ARM, RISC-V) are weakly ordered, for speed (store buffers, caches).

---

Example:

```c
boolean flag = false;  int x = 0;

/* thread 1 */
while (!flag) ;
print x;

/* thread 2 */
x = 100;
flag = true;
```

thread 1 can print 0. Thread 2's two stores touch different variables, so thread 1 may see flag = true before it sees x = 100.

---

A memory barrier (fence) makes every load and store before it complete before any load or store after it:

```c
/* thread 1 */
while (!flag) ;
memory_barrier();
print x;

/* thread 2 */
x = 100;
memory_barrier();   // x is visible BEFORE flag
flag = true;
```

---

Notice: a barrier doesn't lock anything. It only stops reordering across one point.

Peterson becomes correct again if you put a barrier after:

```c
flag[me] = true;
turn = other;
memory_barrier();   // <- here, before the while check
while (flag[other] && turn == other) ;
```

12. Test-and-set (TAS)

The 9a lock variable failed because test `while (lock == 1)`
and set `lock = 1` were two separate steps.

So the hardware provides one instruction that does both:

```c
/* executed ATOMICALLY by the hardware:
   nothing can get in between */

boolean test_and_set(boolean *target) {
    boolean rv = *target;   // read the OLD value
    *target = true;         // always write true
    return rv;              // hand back the old value
}
```

---

```c
do {
    while (test_and_set(&lock))  // old value true  -> someone holds it -> spin
        ;                        // old value false -> it WAS free, and I just set it -> I own it
    /* critical section */
    lock = false;                // release
    /* remainder section */
} while (true);
```

---

Why the race disappears:

it's one uninterruptible read-modify-write. If two CPUs call it at the same moment, the hardware runs them one after the other. The first one reads false and wins, and the second one reads true (the first already wrote it) and spins.

Notice: writing true when the lock is already held is harmless, because it was already true.

Notice: on one CPU, a spin lock needs a preemptive scheduler. Without a timer, the spinning thread never gives up the CPU, so the holder never runs to release the lock.

13. Compare-and-swap (CAS)

```c
/* executed ATOMICALLY by the hardware */
int compare_and_swap(int *value, int expected, int new_value) {

    int temp = *value;          // read the old value

    if (*value == expected) {
        // only if it still holds what I expected...
        *value = new_value;     // ...write the new value
    }

    return temp;                // ALWAYS return the old value
}
```

---

CAS has three operands: the location, the expected value, and the new value. It writes only if nobody changed the location since you looked.

As a lock:

```c
while (true) {

    // "if lock is 0, make it 1"
    while (compare_and_swap(&lock, 0, 1) != 0) {
        ;   // got back non-0 -> someone holds it -> spin
    }

    /* critical section */
    lock = 0;
}
```

---

Two CAS instructions issued at once are carried out one after the other, in some order.
Only the thread that gets back 0 wins.

---

TAS vs CAS:
TAS always writes true.

CAS writes only if the value matches, which makes it more general. It can do "update only if unchanged" for any value, not just a 0/1 lock.

14. Atomic variables (atomics in the language)

Languages expose these instructions as atomic_int, atomic_bool, and so on.

An increment with no lock:

```c
void increment(atomic_int *v) {
    int temp;
    do {
        temp = *v;      // 1. read the current value
    } while (temp != compare_and_swap(v, temp, temp + 1));
                        // 2. write temp+1 ONLY if v is still temp
                        // 3. if someone changed it (CAS returned something else), go back to 1 and retry
}
```

(it is ONE do-while loop: the "while" at the bottom is the loop condition, there is no separate spin loop)

Notice: this do while loop ensures that between my read and my write nothing changed, meaning when I do write it is safe.

---

The idea (the prof's class example): v = 500. I read 500, spend some time computing, and want to write my result back. I'm only allowed to write if 500 is still there. If someone changed it, my computation was based on a stale value, so I redo it with the new value.

Compare this with EXP 9.1. The lost update came from storing a result computed from a stale load. CAS refuses that store, so there are no lost updates. It's also lock-free: nobody holds a lock, and a thread that loses just retries.

Notice: atomics protect ONE variable. "Insert into a queue, then update a count" is two variables, and the gap between them is still a race. Multi-step critical sections still need a lock.

15. The xv6 spinlock

```c
// kernel/spinlock.c
acquire(lk):
    push_off();                         // turn interrupts OFF on this CPU
    if (holding(lk)) panic("acquire");  // I already hold it? bug -> panic
    while (__atomic_exchange_n(&lk->locked, 1, __ATOMIC_ACQUIRE) != 0)
        ;                               // = RISC-V amoswap.w.aq = test-and-set

release(lk):
    __atomic_store_n(&lk->locked, 0, __ATOMIC_RELEASE);   // fence rw,w ; sw zero
    pop_off();                          // interrupts back on (if they were on before)
```

- Atomic swap writes 1 and returns the old value. That's test-and-set in one RISC-V instruction (amoswap).
- ACQUIRE and RELEASE are barriers: the critical section's loads and stores can't move outside the lock. So when the next CPU gets the lock, it sees everything the last holder wrote.
- Interrupts stay off while the lock is held (see EXP 9.3 part 3 for why).
- Example from 9a: allocpid() takes pid_lock around nextpid++, so two forks never get the same pid.
- Linux has spinlocks too, plus sleeping mutexes and semaphores for longer waits (that's 9c).

Rule: spin when the wait is short. Sleep when it's long.

1. Rewrite the lock-variable attempt (9a section 6) using test_and_set(). Which lines change, and why does the race disappear?

Before (9a, broken):

```c
while (lock == 1)   // test
    ;
lock = 1;           // set   <- a switch can land between test and set
/* critical section */
lock = 0;
```

After:

```c
while (test_and_set(&lock))   // test AND set in ONE instruction
    ;
/* critical section */
lock = false;                 // release: unchanged
```

What changed: the two entry lines (the test loop + the set) merge into ONE line.
The release line stays the same (a single store is already one step).

Why the race disappears: the gap between test and set is gone. There is no point where a switch can
land "after I saw 0 but before I wrote 1". If two threads call it together, the hardware runs them
one after the other: exactly one gets back false (and owns the lock), the other gets back true and spins.

Same interleaving that broke 9a, now:

P0  test_and_set(&lock)   returns false, lock is now true -> P0 enters
    -- switch --
P1  test_and_set(&lock)   returns true (P0 already set it) -> P1 spins
    -- switch --
P0  ... CS ... lock = false
    -- switch --
P1  test_and_set(&lock)   returns false -> P1 enters

Even if the switch lands right after P0's call, the lock is ALREADY true -> no second winner.

2. Two threads run increment() on the same atomic_int at once. Trace a round in which one thread's CAS fails. What does that thread do next?

v starts at 5. Both want to add 1 -> correct answer is 7.

T1  temp1 = *v                       temp1 = 5
T2  temp2 = *v                       temp2 = 5      (both read 5: same start as the EXP 9.1 race)
T1  CAS(v, 5, 6)   v is 5 == expected 5 -> v = 6, returns 5
    5 == temp1 -> loop ends, T1 done
T2  CAS(v, 5, 6)   v is 6 != expected 5 -> NO write, returns 6
    6 != temp2 (5) -> CAS FAILED -> loop again
T2  temp2 = *v                       temp2 = 6      (re-read the NEW value)
T2  CAS(v, 6, 7)   v is 6 == expected 6 -> v = 7, returns 6
    6 == temp2 -> loop ends, T2 done

final v = 7 ✓ (plain counter++ could have given 6: T2's stale store would overwrite T1's)

What the failing thread does next: it does NOT block or sleep. It goes back to the top of the do-while,
re-reads the current value, recomputes temp + 1, and tries the CAS again.
Each failure means someone else succeeded, so the system always makes progress (lock-free).
Under heavy contention a thread may retry several times.

3. xv6 turns interrupts off before spinning in acquire(). Describe what happens on one CPU if it didn't, and an interrupt handler took the same lock.

Real xv6 example: tickslock. clockintr() (the timer interrupt handler) does acquire(&tickslock); ticks++;
and the sleep() system call also takes tickslock.

Without interrupts off, on ONE CPU:

1. process P is in the kernel, calls acquire(&tickslock), gets it (locked = 1), is in the CS
2. the timer interrupt fires -> the CPU stops P and jumps into the handler, ON TOP of P
3. the handler calls acquire(&tickslock) -> locked is 1 -> it spins
4. P is the only one who can release the lock, but P can't run until the handler RETURNS
5. the handler can't return until it gets the lock
-> the handler spins forever, the CPU is stuck: DEADLOCK (the machine hangs)

(this is the 9.2 lesson in its worst form: on one CPU, while you spin, the holder is NOT running,
and here it never will be)

With interrupts off (push_off in acquire):
the interrupt can't be delivered while P holds the lock. It stays pending.
P finishes the CS, release() -> pop_off() turns interrupts back on -> NOW the handler runs,
finds the lock free, and gets it.

On multicore: a handler on ANOTHER CPU that wants the lock just spins briefly until the holder's CPU
releases it -> fine. The danger is only the handler on the SAME CPU as the holder.

(holding(lk) + panic in acquire catches a related bug: the same CPU acquiring a lock it already holds,
which would also spin forever)

======================

Bonus (in-class activity): one core -> spins per acquire = 0. Why?

"A spin is a CPU waiting for another CPU." With one core there is no other CPU.
And xv6 holds every spinlock with interrupts OFF, so the holder can't be preempted (no timer switch)
and no interrupt handler can run on top of it. Nobody else can run until it releases.
So whenever anyone calls acquire, the lock is already free -> it gets it on the first try -> 0 spins.
With two cores, the other core runs at the same time and can find the lock held -> spins > 0.
