```c

    acquire(lock);
    /* critical section */

    /* remainder section */
}


acquire() {                    release() {
    while (!available)             available = true;

```

this is the simplest tool the OS offers: acquire to enter, release to leave. Each of acquire() and release() must itself be atomic (built from TAS/CAS, as in 9b).

Contention:
when many threads want the lock at once, all but one wait, and the cost grows with the number waiting.

Duration:
if the lock is held briefly, busy waiting is fine. If it's held for a long time, waiters should sleep. That's what the rest of this round is about. (there are better solution than the spin wait)

18. Blocking semaphores: sleep instead of spin !

```c

// semaphore itself is just a c struct

struct semaphore {
    int count ;
    queue q ;
}

void wait(semaphore s ){

    s.count--;

    // place into q
    if(s.count < 0) {
        put this process in s.q;
        block this process; // block means sleep this process
        // no cpu use, no spinning
    }

}

void signal(semaphore s) {

    s.count++;

    // release from queue
    if(s.count <= 0){
        remove a process P from s.q;

        put P on the ready list; // ready here is the scheduler
        // this wake up the process
    }
}



```

The 4 rules (from tutorial 3):

(1) wait() may block (sleep the process when <0 )

(2) signal() NEVER blockes

(3) You cannot "read" a sepaphore's balue .
There is no if (semaphre_s == 0).

you can only call wait() and signal()
and set the inital value of the s

(4) A negative count = the number of blocked process

for example :

-2 means there are 2 process that are asleep in the queue

20. Pattern: signalling (T3)

Goal:
make sure A's statement a1 happens before B's statement b1.

```c

sem = Semaphore(0);

/* thread A */          /* thread B */
a1;                     sem.wait();    // blocks until A signals
sem.signal();           b1;


```

Notice the case when arrive :

If B arrives first, it blocks at 0 until A signals.

If A arrives first, the signal is remembered (count becomes 1), so B passes straight through.

Notice: a semaphore remembers a signal. That's a key difference from condition variables (section 26).

--

my quetsion :

if a semaphore can be "resued" why not just alwasy semaphore (0) and call signal to get the number up ???

Answer:

You can. A semaphore started at N behaves the same as one started at 0 and then signalled N times before anyone waits:

```c

s = Semaphore(3);          // same result as:
                           s = Semaphore(0);
                           s.signal(); s.signal(); s.signal();


```

So why use the starting value?

(1) timing: the extra signals must happen BEFORE anyone waits. A thread that waits too early would block
wrongly. The starting value is set when the semaphore is created -> correct before any thread runs.

(2) you can't forget it: Semaphore(0) for a mutex + a forgotten signal() -> the first wait blocks forever (deadlock).

(3) the starting value says what it MEANS: 0 = event not happened yet (signalling must start at 0, an
early signal would let B through before A did a1), 1 = one inside (mutex), N = N free slots.

A semaphore remembers every signal: count = start value + all signals - all waits.

21. Pattern: rendezvous (T3)

Goal:
neither thread continues past the meeting point until both have arrived.

That means a1 and b1 both happen before a2 and b2.

```c

aArrived = Semaphore(0);
bArrived = Semaphore(0);

/* thread A */              /* thread B */
a1;                         b1;

aArrived.signal();          bArrived.signal();   // 1. say "I'm here"
bArrived.wait();            aArrived.wait();     // 2. then wait for the other

a2;                         b2;


```

(T3 fix): your notes have wait() first, then signal(), in both threads.

That's the broken version.
If both threads wait first, each blocks waiting for a signal the other will never send, because the signal comes after the wait: deadlock.

The rule:
signal first, then wait.

It's the same idea as Peterson: announce yourself before you wait. (If only one of the threads waits first, it still works, but it may cost an extra context switch.)

23. Pattern: barrier (T3)

Goal:

n threads each reach a point, and nobody continues until all n have arrived. The last one to arrive lets everyone through.

```c

n = 4;  count = 0;
mutex   = Semaphore(1);
barrier = Semaphore(0);     // locked until everyone is here


// for "mutex" s(1) semaphore , use wait() and signal()
// to envalope the critical section


mutex.wait();
    count = count + 1;      // shared counter -> protect it with the mutex
mutex.signal();



// for D when the count reach N trigger signal()
if (count == n){
    // the last one to arrive opens the barrier
    barrier.signal();
}


barrier.wait();             // this pair is a "turnstile":
barrier.signal();           // pass through, then let the next one through


```

A, B and C arrive and block on barrier.wait()
(the BARRIER semaphore goes 0 -> −1 -> −2 -> −3; the variable count goes 1, 2, 3. two different counters!).

D arrives, count == 4, so it signals. One thread wakes, passes the turnstile, and its own signal wakes the next, and so on, until all 4 are through

---

Notice (your note was right):
when everyone has passed, barrier is left at 1,

so the barrier is not reusable.

A second round would pass straight through.
A reusable barrier needs a two-turnstile version.
(fix: "just call one extra wait() to bring it back to 0" is the right idea, but WHO calls it and WHEN?
if a fast thread loops around into round 2 before the last thread has passed, it can slip through.
the two-turnstile barrier solves that: a 2nd turnstile that everyone must pass before round 2 starts;
not needed in detail for now.)

24. Producer/consumer (bounded buffer)

Three problems to solve:

(1) Changes to the buffer must be race-free (a mutex).

(2) Overflow: the producer must stop when the buffer is full.

(3) Underflow: the consumer must stop when the buffer is empty.

---

Infinite buffer (T3):
there's no overflow, so you need only a mutex and an item count.

```c

    // here we have 2 semaphore , one used as mutex , one items

    mutex = Semaphore(1);  items = Semaphore(0);

    /* producer */               /* consumer */
    event = waitForEvent();      items.wait();       // underflow: sleep if empty
    mutex.wait();                mutex.wait();
    buffer.add(event);           event = buffer.get();
    mutex.signal();              mutex.signal();
    items.signal();              event.process();


```

---

Bounded buffer with N slots (the lecture's names; T3 calls empty "spaces" and full "items")

```c

semaphore mutex = 1;   // protects the buffer itself
semaphore empty = N;   // counts EMPTY slots  (T3: spaces)
semaphore full  = 0;   // counts FULL slots   (T3: items)

producer() {                    consumer() {
  while (TRUE) {                  while (TRUE) {
    item = produce_item();          wait(&full);     // sleep if nothing to take
    wait(&empty);  // sleep if full  wait(&mutex);
    wait(&mutex);                   item = remove_item();
    insert_item(item);              signal(&mutex);
    signal(&mutex);                 signal(&empty);  // one more empty slot
    signal(&full);                  consume_item(item);
  }                               }
}                               }


```

empty stops the producer when the buffer is full. It sleeps, not spins

full stops the consumer when the buffer is empty.

Each signal() wakes a waiting process if there is one; otherwise it just raises the count.

Order matters:
wait for the resource(empty/full) before taking the mutex. EXP 9.4 shows what happens otherwise.

25. Monitors

Semaphores are easy to misuse:

swap two wait() calls and the program can deadlock.

A monitor puts the synchronization into a type.

```c

    monitor monitor_name {
        // shared variable declarations
        function P1(...) { ... }
        ...
        function Pn(...) { ... }
        initialization code(...) { ... }
    }



```

Notice:

A monitor is an abstract data type: shared data, the only procedures allowed to touch it, and initialization code.

Only one thread can be active inside the monitor at a time, so mutual exclusion comes for free and you never write wait(mutex).

You enter by calling one of its procedures. Other threads wait in the entry queue.

=====================

26. Condition variables: waiting inside a monitor

cwait(c)

puts the caller to sleep on condition c and lets another thread into the monitor. A sleeping thread doesn't count as "inside".

csignal(c)

wakes one thread waiting on c. If nobody is waiting, the signal is lost. It is not remembered, unlike a semaphore's signal (section 20).

======================

There are two kinds of semantics for what happens after csignal:

(1) Hoare:
the woken thread runs immediately, and the signaller waits in an urgent queue. The condition is guaranteed true when the woken thread runs.

(2) Mesa:
the signaller keeps running, and the woken thread runs later. By then the condition may be false again. Almost every real system uses Mesa.

====================

The bounded buffer as a monitor:

```c

// produce and consumer



void append(char x) {                  void take(char *x) {
    if (count == N) cwait(notfull);        if (count == 0) cwait(notempty);
    buffer[nextin] = x;                    *x = buffer[nextout];
    nextin = (nextin + 1) % N;             nextout = (nextout + 1) % N;
    count++;                               count--;
    csignal(notempty);                     csignal(notfull);
}                                      }


```

Notice:

There are two condition variables, notfull and notempty.

There's no lock in this code, because the monitor already allows only one thread inside.

The if is correct under Hoare.

Under Mesa it must be while: re-check after waking. You'll trace why in EXP 9.4.

27. xv6: sleep() and wakeup()

```c

// kernel/pipe.c, piperead(): wait for data

acquire(&pi->lock);

while (pi->nread == pi->nwrite && pi->writeopen) {   // pipe is empty
    ... if killed, release and return -1 ...

    sleep_prepare(&pi->nread);   // register on a channel FIRST
    release(&pi->lock);
    sleep();                     // block, unless already woken
    acquire(&pi->lock);
}
... copy bytes out ...
wakeup(&pi->nwrite);             // a writer may continue now
release(&pi->lock);


```

xv6 has no semaphores and no monitors.

A process sleeps on a channel, which can be any address

(here &pi->nread),

and wakeup(channel) makes all the sleepers on it RUNNABLE.

That's L03's SLEEPING → RUNNABLE.

---

The while re-checks after waking:
that's Mesa semantics.

No lost wakeup: sleep_prepare() registers before the lock is released. If a writer's wakeup arrives in the gap before sleep(), it clears the registration, and sleep() returns at once. Without this, the reader could miss the wakeup and sleep forever. (It's the same kind of gap as 9a, now between "decide to sleep" and "actually sleep".)

---

A sleeplock is a mutex that sleeps instead of spinning: a spinlock, a flag, and sleep().

28. Dining philosophers (T3)

Five philosophers sit at a round table,
with five forks, one between each pair

Each one loops forever: think, then eat.

Eating needs both neighbouring forks !

The goal is to let as many eat at once as possible, with no deadlock.

---

The naive solution

(T3 fix for the code:

it should be (i+1) % 5, not (i++) % 5, and the last line should be signal, not wait):

```c

// 5 fork
semaphore fork[5] = {1, 1, 1, 1, 1};

// each philospher just loop
// think -> wait for left is unblocked
// -> wait for right fork is unblocked
// -> eat

// signal both left and right is realieased

philosopher(i) {
    while (true) {
        think();
        fork[i].wait();             // left fork
        fork[(i + 1) % 5].wait();   // right fork
        eat();
        fork[i].signal();
        fork[(i + 1) % 5].signal();
    }
}



```

Notice:

It allows up to 2 at once (5 forks / 2 per eater = 2). Its real problem is deadlock:

if all 5 pick up their left fork at the same moment, every right fork is taken, and everyone waits forever.

---

Fix 1,
the footman (your f = some-value):

f = Semaphore(4), so at most 4 philosophers may try to eat at once.

```c

f.wait();       // at most 4 at the table
...take forks, eat, put forks down...
f.signal();



```

With 4 philosophers and 5 forks,
at least one of them can get both forks, so there's no deadlock.

---

Fix 2, asymmetry:
one philosopher picks up the right fork first.
The circular wait is broken.

The maximum eating at once is still 2,
limited by the number of forks.
The fixes remove the deadlock;
they can't create more forks.
