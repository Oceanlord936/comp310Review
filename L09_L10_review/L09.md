Give an interleaving that ends at each possible balance ($50, $100, $150).

Each update is 3 instructions, with its own private register:

Only the mixing BETWEEN the two can change.

Key idea: if BOTH loads happen before EITHER store, both start from the same old 100,
and whoever STORES LAST overwrites the other one -> one update is lost.

A2 rA = 50
A3 balance = 50

B3 balance = 100

(b) $50: both load 100, A stores last -> B's deposit is lost

A1 rA = 100
B1 rB = 100 <- B loads before A stores
B2 rB = 150
B3 balance = 150
A2 rA = 50 (A still holds the OLD 100 in its register)
A3 balance = 50 <- A stores last, overwrites B's 150

3. If each update were a single atomic instruction, how many final balances would remain?

ONE: only $100. ✓ (my answer)

Atomic = the load, compute and store happen as one step, nothing can run in the middle.
So there is no gap between load and store, and nobody can work from a stale value.

Only 2 orders are left:
A then B: 100 - 50 = 50, then 50 + 50 = 100
B then A: 100 + 50 = 150, then 150 - 50 = 100

Both give 100 (adding and subtracting can be done in any order).

Notice: atomic removes LOST UPDATES. It does not fix everything: if the two operations
don't commute (A = B + 1 vs B = B \* 2), the order can still change the result.
That's why bigger critical sections need a lock, not only atomic single steps.

1. For each attempt, give an interleaving that shows the FIRST of the four requirements it violates.

Recall the 4 requirements:
(1) mutual exclusion (2) no assumptions about speed / number of CPUs
(3) progress: nobody OUTSIDE its CS blocks another (4) bounded waiting: nobody waits forever

How to build the interleaving: find the GAP in the entry code (between a test and a set),
and put a context switch right there.

---

(a) Lock variable -> breaks (1) mutual exclusion

the gap: between "while (lock == 1)" (test) and "lock = 1" (set). lock starts at 0.

P0 while (lock == 1) reads 0, leaves the loop
-- switch --
P1 while (lock == 1) reads 0, leaves the loop
P1 lock = 1
P1 enters CS
-- switch --
P0 lock = 1 (P0 already passed the test, it never looks again)
P0 enters CS -> BOTH in the CS

---

(b) Check-then-set flags -> breaks (1) mutual exclusion

same gap: between checking the other's flag and raising my own. both flags start false.

P0 while (flag[1]) flag[1] is false, leaves the loop
-- switch --
P1 while (flag[0]) flag[0] is false, leaves the loop
P1 flag[1] = true
P1 enters CS
-- switch --
P0 flag[0] = true
P0 enters CS -> BOTH in the CS

---

(c) Set-then-check flags -> mutual exclusion holds, breaks (3) progress (and then (4))

the gap: between raising my flag and checking the other's.

P0 flag[0] = true
-- switch --
P1 flag[1] = true
P1 while (flag[0]) true -> spins
-- switch --
P0 while (flag[1]) true -> spins
... both spin forever = DEADLOCK

nobody is in the CS, yet each one (still outside its CS, in the entry code) blocks the other
-> (3) fails; and since they wait forever, (4) fails too.

---

(d) Strict alternation -> mutual exclusion holds, breaks (3) progress

turn starts at 0. P1 has a very long non-critical section (or stops wanting the CS).

P0 while (turn != 0) turn is 0, enters
P0 CS, then turn = 1
P0 non_critical() (short)
P0 while (turn != 0) turn is 1 -> spins
P1 ... still in its long non_critical(), never enters, so never sets turn = 0
P0 spins forever, even though the CS is EMPTY

P1 is outside its CS and still blocks P0 -> (3) fails.
(the two must strictly take turns: a fast process is held to the speed of a slow one)

Summary:
lock variable -> (1)
check-then-set flags -> (1)
set-then-check flags -> (3) deadlock (then (4))
strict alternation -> (3)

My understanding (in plain words):

(1) lock variable / check-then-set flags: UNSAFE
the lock (or the flag) is itself shared data, and "test it, then set it" is 2 steps.
so the lock itself is now a critical section, with nothing protecting it.
-> the race just moved into the lock.
(adding another lock in front doesn't help: that lock has the same test/set gap, forever)

(2) set-then-check flags: SAFE but STUCK
raising my flag first closes the gap, so mutual exclusion holds.
but it is still 2 steps, and it quietly assumes one process raises its flag BEFORE the other.
not the case: if both raise together, each waits for the other,
there is no tie-breaker, nobody lowers its flag first -> locked each other = DEADLOCK.
-> Peterson = this + a tie-breaker ("turn": when both want in, the last one to write turn waits)

(3) strict alternation: SAFE but STUCK
no race, but it assumes the two processes take turns in lock-step (P0, P1, P0, P1 ...).
real processes don't: one may want the CS 10 times while the other is busy elsewhere.
the fast one is held hostage by the slow one -> breaks (3).
(the root cause is assuming equal speed = the spirit of requirement (2))

Common lesson:
every failed attempt hides an assumption about TIMING or ORDER
("one goes first", "they alternate", "nobody switches between my test and my set").
a correct solution must work under EVERY possible interleaving.

Two ways out:

- software: Peterson (clever ordering + turn), but only if loads/stores are not reordered
- hardware (9b): make "test and set" ONE indivisible instruction -> no gap -> the lock variable idea works

2. One CPU, preemptive RR. Single-threaded: 2 s critical section + 6 s other work = 8 s.
   Split evenly over 2 threads with a busy-waiting lock. Under 8 s? When does spinning add time?

Each thread: 1 s CS + 3 s other work. Total CPU work is still 1+3+1+3 = 8 s.

NO, it can't finish under 8 s.
ONE CPU runs one thread at a time, so splitting the work into threads does not make it
run in parallel. 8 s of work needs at least 8 s of CPU. Best case = 8 s (+ switch overhead).
(threads only help with more CPUs, or when one thread waits on I/O while the other computes)

When does spinning add time?
when a thread wants the lock while the OTHER thread holds it. On one CPU that can only happen
if the holder was PREEMPTED in the middle of its CS (the timer fired), and RR now runs the waiter.

Key point: on one CPU, while the waiter spins, the holder is NOT running.
So the lock can't be released during the spin: every spin quantum is pure waste.

Example (prof's class example): A is in its 1 s CS, and B wants the lock.
RR alternates quanta: A, B, A, B ...
A's quanta: A finishes its 1 s of CS work
B's quanta: B spins (useless)
-> A's 1 s CS stretches to 2 s of wall time (it only gets 50% of the CPU),
and B burns 1 s spinning -> total 8 + 1 = 9 s.

- the CSs never collide (each thread is outside its CS when it gets preempted) -> 8 s
- one CS fully overlapped by the other spinning -> 9 s
- both CSs overlapped -> up to 10 s

Fix (round 9b): a lock that SLEEPS (blocks) instead of spinning. B blocks, gives the CPU back,
A finishes its CS at full speed, release() wakes B -> back to 8 s.
Rule: spin only if the wait is short AND the holder is running on ANOTHER CPU.

The two variables do two different jobs:

- true -> the other wants in too -> the flag alone can't decide (that's why the
  set-then-check attempt deadlocked) -> ask turn

turn = the TIE-BREAKER, only matters when BOTH flags are up

- each thread writes turn = other ("you go first")
- turn holds ONE value, and a later write overwrites an earlier one
  -> whoever wrote turn LAST is the one that waits
- usually the late arrival is also the last writer of turn, so "the late one waits",
  but strictly it's turn that decides (if both arrive at almost the same time,
  both flags are up and the last turn write settles it)
- both can never wait together: me waits only if turn == other, other waits only
  if turn == me, and turn can't be both -> no deadlock

SWAPPED order (broken):

    turn = other;                            // give the turn away FIRST
    flag[me] = true;                         // say I'm here only AFTER
    while (flag[other] && turn == other) ;

the gap: between "turn = other" and "flag[me] = true", my turn write exists but my flag
is still false. if the other thread runs in that gap:

me: turn = other
-- switch (my flag is still false!) --
other: turn = me (other is now the LAST writer of turn)
other: flag[other] = true
other: while (flag[me] && turn == me) flag[me] is FALSE -> "me isn't here" -> ENTERS
-- switch --
me: flag[me] = true (too late, other already decided)

turn write, my flag is already up, and the gap is gone.

One line: flag = "am I here?", turn = "who yields if we both are?"

Core idea of Peterson: A LATER WRITE OVERWRITES AN EARLIER ONE

both threads give the turn away (turn = other), but turn holds only ONE value,
so the second give-away overwrites the first.
-> the LATER writer's politeness is the one that sticks -> the later writer waits, the earlier one goes.

(strictly: "later" = wrote turn later, not arrived later. even if both arrive at the same
instant, one of the two writes to turn always lands second -> never a deadlock)

Step 3 check, in full:

- flag[other] is down -> no tie -> I go
- flag[other] is up -> tie -> look at turn:
  turn == other -> I wrote last (I yielded last) -> I wait
  turn == me -> the other wrote last (it yielded to me) -> I go
